## 1. プロダクト目的 (Why)

NEO ACADEMIA 受講企業の Customer Success 活動を、属人化させずに**入力 → 健全性可視化 → 解約予兆検知 → 介入**まで一つのポータルで回す。

- **解こうとしている課題**: 複数事業にまたがる顧客を一括管理しつつ、コミュニティ運営の観点を取り込んだ独自指標で健全性を可視化する。
- **代替手段に対する優位**: 汎用 CRM (Salesforce 等) では「コミュニティ」軸の指標 (参加状況・アンケート・出席・週次レビュー等) を一級市民として扱えない。NEO ACADEMIA 固有の業務フローと指標を中心に据える必要がある。

## 2.5 取り扱う事業 (4 本柱)

本ポータルは以下 **4 つの事業の顧客企業を一括管理**する。各事業は契約サイクル・更新ロジック・コミュニティ関与の測り方が異なるため、共通モデルに無理に押し込まず**事業ごとの特性を保持しつつ横断で見られる**設計が必要。

### 1. NEO ACADEMIA (主軸 / コミュニティの母体)
- 契約周期: **1 年**
- コース: リーダー育成 / PJT 共創 (今後増える可能性あり。1 期はコース分けなし)
- アップセル: 期間限定 (例: 3 ヶ月) の事業伴走
- 定例面談: 年 3 回 (企業との節目)
- 参加者構造:
  - **企業選抜生** (メイン)
  - 担当者 / 担当責任者 / 決裁者 / 担当役員
- **アカデミア会員企業は九州未来評議会の参加権を自動付与**
- 個別出欠管理は**別アプリ** (現在制作中) → 将来 API 連携

### 2. 九州未来評議会
- 契約周期: **1 年**
- 参加者: **評議員** (※アカデミア会員企業の権利 + 独立した評議会会員企業)
- 定例面談なし。**契約更新のための商談は必要**
- 年 10 回程度の講座 + 懇親会 + イベント
- コミュニティ関与度算出は**別アプリ** (出席・懇親会・イベント) と連携予定

### 3. AI リスキリングキャンプ
- 形態: **単発の AI 研修**
- リードタイム: 1.5 ヶ月前に内諾、1 ヶ月前までに助成金申請 (← 業務 SLA)
- コース: Basic / Advance
- アップセル (将来): 実装伴走サポート (期間限定)
- 受講パターン: 連続受講もあれば飛び飛びもあり
- 更新判断指標: **年間受講者数 / 社員数比率 / 実装サポートまでのロードマップ達成度**
- 営業観点: アップセル・追加受注の動線管理が必要

### 4. コミュマネの学校
- 形態: **3 ヶ月の研修**(年に複数回開催)
- 1 期あたり講義 6 回
- 契約→受講開始まで 1 週間で OK (リードタイム短)
- 組織で繰り返し受講するモノではない (1 回完結)

### 事業間の関係

```
NEO ACADEMIA ──(会員権利として付与)──→ 九州未来評議会
            ↑ 独立で参加する企業もある  ↑

AI リスキリングキャンプ (独立事業)
コミュマネの学校 (独立事業)
```

### コミュニティ関与度 (全事業共通の軸)

4 段階で管理: **コア / アクティブ / カジュアル / 離脱危機**

理論的根拠は [COMMUNITY.md §4 メンバーシップの分布](COMMUNITY.md#4-メンバーシップの分布--既存のコミュニティ関与度-4-段階の根拠)。コミュニティの典型的分布:
- コア: 5〜10%、運営を指導的に導く
- アクティブ: 10〜20%、定期参加
- カジュアル (周辺): 65〜75%、見守り中心
- 離脱危機: 接点が途絶しつつある層 (※定義の正式化は TBD)

> ⚠️ **設計原則**: 「全員が本気である必要はない」。未入力・未参加を一律ネガティブ扱いしない。コアへの**登り方**を可視化し、カジュアル層を**包摂**することが鍵。

### 業務指標フレームワーク

ヘルススコア・各種 KPI は **2026 CCC Framework (Retention / Contribution / Support & Efficiency / Growth / Relevance)** の 5 本柱に沿って設計する。現行の `lib/domain/health.ts` は #1 Retention の一部のみで他柱が欠落しているため、Phase 2 で再設計予定。詳細: [COMMUNITY.md §9](COMMUNITY.md#9-コミュニティ-roi-測定-2026-ccc-framework--指標設計の正本)。

### 用語統一 (本ドキュメント以下で固定)

- **事業 (business)** — 4 事業 (NEO ACADEMIA / 九州未来評議会 / AI リスキリングキャンプ / コミュマネの学校) の総称。コード上の英語キーは `business`。
- **期 (cycle)** — NEO ACADEMIA / 九州未来評議会 / コミュマネの学校 で使う運営単位。
- **回 (round / session)** — AI リスキリングキャンプで使う運営単位 (第◯回)。
- **期と回は別概念** として扱う。共通の上位概念があるかは設計時に検討。

## 2.6 コア機能要件 — 少人数で CS を回すための 7 本柱

> **運用哲学**: 「**ユーザーが行う業務を AI が代替する**」。CS 業務の自動化と判断補助を中核に据え、人間は最終確認とコミュニティへの介入に集中する。CCC Framework 5 つの罠のうち「リーダー二重負担」「投資の測定錯覚」を構造的に解く。

スコープは**内諾以降**。営業フェーズ (内諾前) は対象外。

### F1. オンボーディング状況の可視化
- 内諾 → 助成金申請 (AI リスキリングのみ) → 契約締結 → 受講開始までの**各マイルストーン到達状況**を企業 × 事業 × 期/回ごとに一覧表示
- 期限超過 / 滞留 の自動アラート
- 事業ごとにフェーズ定義が異なる (例: AI リスキリングは 1.5 ヶ月前内諾 / 1 ヶ月前助成金) → 事業ごとのオンボテンプレートを定義

### F2. コホート (期/回) 一括管理 (※一斉送信は対象外)
- 同じ期/回の対象企業を**横断ビュー**で管理:
  - イベント招待状況 / 出欠の集約
  - 面談日程調整の進捗 (1 to N で個別調整、一斉送信ではない)
  - 期初・期中・期末の節目で「誰に何を送ったか/送っていないか」を一覧
- ⚠️ **メールの一斉送信機能は持たない**。送信は Gmail 個別送信ベースで、ポータルは**送信履歴を企業ごとに突合**する

### F3. Gmail リアルタイム連携 + AI 自動判定
- **受信・送信の両方**をリアルタイムで取り込み (現状: 30 分 cron / 受信のみ → 改善余地)
- **送信メールも企業ごとに自動振り分け** — ユーザーが Gmail で送ったメールがポータル上の該当企業のカルテに自動で紐付く
  - To/Cc のメールアドレス + 件名 + 本文を AI が照合して企業を特定
  - 振り分け不能なら未割当キューに溜め、人間が手動アサイン
- AI (Claude) がメール内容を解析:
  - **どの企業 / どの事業に紐づくか**を自動判定
  - **顧客ステータスの変化**を推測 (例: 不満の兆候、契約更新意向、紹介示唆)
  - **次に取るべきアクション**をユーザーに提案
- 返信は AI が**ドラフト生成 → 人間が確認して送信** (送信は人間のクリック必須)

### F4. Drive テンプレート連携 + 送付履歴
- 事業ごとに共通の送付資料 (案内 / 申込書 / 助成金書類 / オンボ資料 等) を Google Drive で管理
- ポータルから**該当テンプレを即検索 → 編集 → 送付**できる動線
- **誰に / いつ / どの版を送ったか**の履歴を自動記録
- 過去送付資料は企業カルテから遡れる

### F5. 企業 × NEO 関係性の可視化 → パートナー化
- 企業ごとに NEO との接点・歴史・コアメンバー候補を可視化
- 単なる「顧客管理」ではなく**コミュニティの一員としてパートナー化していく道筋**を見せる
- コア候補 → アクティブ → パートナー (共創相手) への「Inner Rings 動線」 ([COMMUNITY.md §3](COMMUNITY.md))

### F6. 顧客の声 (VoC) もれなく対応 + 継続ステータス
- メール / 議事録 / アンケート / 出席アプリ等から**顧客の声を抽出 → 一元集約**
- AI が分類 (要対応 / FYI / ポジティブ) → **取りこぼしゼロ運用**
- 各企業の**現在の継続ステータス** (継続意向 / 検討中 / 解約懸念) を常時表示・更新

### F7. アンケート連携 + 関与度判定
- 外部ツール (Google Forms / Typeform 等) で取得したアンケートを**取込・保存・分析**
- AI が回答内容を解析 → コミュニティ関与度 4 段階 (コア/アクティブ/カジュアル/離脱危機) の**判断材料**として組み込む
- CCC Framework の **Relevance** (回答率・コメント量) と **Retention** (満足度トレンド) に貢献

---

### 機能間の連携 (データの流れ)

```
[Gmail] ──┐
[Drive ] ──┼──→ [AI 解析・判定]──→ [企業カルテ更新]──→ [関与度・ヘルススコア]
[出席app] ─┤              ↓
[アンケート] ┘         [ユーザーへの提案]
                            ↓
                    [人間が確認 → アクション]
```

**設計原則**:
- AI は判定・提案・ドラフトに徹し、**最終アクションは人間**
- 「もれなく」が運用の生命線 — 何かを見落とすと顧客との関係が崩れる
- 業務テンプレ (オンボ / 一斉連絡 / 資料送付) は事業ごとに定義しつつ、横断で見られる構造

## 4. スコープ管理

## 5. 成功指標 (KPI)

このプロダクトを評価する指標 (ポータル自体の評価軸 / プロダクトとしての価値ではなく **使ってもらえているか**):

- **ユーザー使用率** — DAU / WAU、ログイン頻度、主要画面の到達率
- **バグ報告数** — 単位時間あたりの不具合報告 (少ないほど良い)

> 業務 KPI (週次入力率 / Churn 率 等) はポータルが計測する**コンテンツ側の指標**であり、本ポータル自体の評価指標とは分けて扱う。

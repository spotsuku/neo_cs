## 0. なぜこれが本ポータルの中心軸なのか

NEO ACADEMIA / 九州未来評議会 / AI リスキリングキャンプ / コミュマネの学校 ── これらは **「サービス提供」ではなく「コミュニティ運営」** として設計されている。
したがって本ポータルは汎用 CRM の Customer Success ではなく、**コミュニティマネジメントのための業務基盤**として作る必要がある。

---

## 1. コミュニティの定義

> **コミュニティとは「共有テーマ・価値」を中心に**、自発的・自律的に集まり、想いとコミットメントで連携する集団。
> チームとの違い: チームは組織の目標達成のために上位から役割が割り当てられ、締切に従う。コミュニティは自発的目標で、メンバーが望む限り永続する。

**重要な転回**: 「サボった人がいたら負けるのがチーム / サボっている人が許され、次の出番があるのがコミュニティ」
→ UI 上で「未入力」「未参加」を一律ネガティブに扱わない。離脱予兆と「今は周辺グループにいる」は別物。

---

## 2. コミュニティマネジメント = 集団の行動変容を促すスキル

個人コーチングは「外側のコーチが個人に介入」。
コミュニティマネジメントは **「見えざるコーチが集団内に内在化・分散」** されている状態をつくる。

### 見えざるコーチの 5 種
| 種類 | 例 |
|---|---|
| 神・宗教・推し (Divine Authority) | 信仰、良心 |
| 地域・民族精神 (Regional/National Ethos) | 「日本人らしく」「武士らしく」 |
| 組織文化 (Corporate Culture) | 「うちの会社はそういうもの」 |
| 社会規範・世間体 (Social Norms) | 暗黙の共有認識 |
| 神話・伝統・物語 (Narrative Memory) | 創業ストーリー、武勇伝 |

→ アプリ上で「文化」「物語」「シンボル」を扱う領域を持つことが理に適う (Phase 後段で UI 設計に反映)。

## 3. コミュニティの骨格 (4 要素) — **データモデルの根幹**

| # | 要素 | 意味 | NEO ACADEMIA の例 |
|---|---|---|---|
| 1 | **Shared Value** | 集う人が「前提として大切さを信じる、譲れない価値」 | `Be Playful` |
| 2 | **Membership Identity** | コミュニティの一員だと意識化されて初めて意味を持つ。入会手続き/契約だけでは育まれない | (期生・評議員・受講者 など) |
| 3 | **Moral Proscriptions** | 行動原則。共有価値からインパクトへつなぐためのアクション | ヒーローサイクル (後述) |
| 4 | **Insider Understanding** | 内観 — 内部者だけが共有する文脈・物語・暗黙知 | (用語・通称・歴史) |

> 「何を信じて集まっているのかが一番大事」 (p.32)

### Shared Value 浸透のループ (ダニエル・キムの成功循環)
`Shared Value → 関係の質 → 思考の質 → 行動の質 → 結果の質 → (再び関係の質へ)`

### 所属をつくる 7 原理 (Charles Vogl『The Art of Community』)
1. **The Boundary Principle** — 境界 (外部者と内部者を隔てる)
2. **The Initiation Principle** — 通過儀礼
3. **The Rituals Principle** — 儀式 (意味を定着させる活動)
4. **The Temple Principle** — 神殿 (隔絶された空間)
5. **The Stories Principle** — 物語 (価値を伝える共有された物語)
6. **The Symbols Principle** — シンボル
7. **The Inner Rings Principle** — 内輪 (参加による昇格の道順)

## 4. メンバーシップの分布 — **既存のコミュニティ関与度 4 段階の根拠**

> 「コミュニティには熱量の違う人たちがいる。大事なのは**全員が本気である必要は全くない**」 (p.39)

| 階層 | 比率 | 概要 | アプリ上のラベル (現行) |
|---|---|---|---|
| **コア・グループ** | 5〜10% | プロジェクトを引き受け、テーマを特定し、運営を指導的に導く | **コア** |
| **アクティブ (レギュラー)** | 10〜20% | 定期的にミーティング・イベントに参加。コアほどコミットは高くない | **アクティブ** |
| **周辺 (カジュアル)** | 65〜75% | コア・アクティブの交流を見守る。積極参加はしない | **カジュアル** |
| アウトサイダー | — | 外部者 | (該当する社内ラベルは **離脱危機** に近いが概念は別 — 後述要整理) |

### 設計原則 (UI / 介入ロジックに直結)
- **コアメンバーの声を吸い上げる** 仕組み
- **コアへの登り方を明示する** 導線 (周辺→アクティブ→コア)
- **周辺メンバーを上手に包摂する** こと自体が鍵 (排除しない)
- 「本気になるのは背中を追ったとき」 — ロールモデルの可視化

> ⚠️ **要整理**: 現行アプリの「離脱危機」は分布上の階層ではなく**遷移リスク**。次回会話で「離脱危機 = (1) コアから降りた人 / (2) 周辺で接点が途切れた人 / (3) その両方」のどれかを定義する必要がある。

## 5. コミュニティ参加モデル (Jono Bacon)

メンバーが定着するまでの 6 ステップ。**オンボーディング設計に直結**:

1. なぜ参加するのかを理解する
2. ツールをセットアップする
3. スキルを身につける
4. 既存メンバーと関係を作る
5. 問題解決をする
6. フィードバックを得る

> **習慣化には平均 66 日**。1 期 (12 ヶ月) の中で 66 日を超える接点設計が必要。

## 6. Moral Proscriptions — ヒーローサイクル

行動変容を促すには、**コアメンバーがヒーローとなり背中を追いたくなる**状態をつくる。
「1 人のヒーローが後に続く 1 万人を生む」

```
火を灯す → 火で遊ぶ → 人が集まる → 松明を手に取る → 未到の山を登る
   → 山の上で絶景 → ヒーローとして歓迎 → みんなが成功を語る
   → 案内が広まる → (次のヒーローへ)
```

運営側の介入 (薪をくべる / 風を送る / 地図をつくる / 物語を本にする) を**システム化**できると、属人化を超える。

## 7. コミュニティライフサイクル (動的)

`潜在 → 孵化(今すぐ価値を) → 集中/拡張(成熟) → 所有/受容性 → 変容 → 終わらせる/存続させる`

> 「コミュニティは生き物。脱皮しない蛇は死ぬ」 (p.47)

→ 期 (cycle / 回) のステージを「成熟度フェーズ」として持たせると有効。

## 8. 5 つの構造的な罠 — **これがアプリで対処すべき課題**

> 「リーダーは火を点ける人、コミュニティマネージャー (CM) は火を燃やし続ける人。組織は点火装置に投資し、炉を作らない」

| # | 罠 | メカニズム | アプリでの対処示唆 |
|---|---|---|---|
| 1 | **スターリーダー依存** | リーダー異動でコーチが消える。実態はコーチが内在化されていなかった | コアメンバーの分散・可視化、Shared Value の明文化 |
| 2 | **コンテンツ過多・会話消滅** | リーダーがコンテンツを量産するが応答がない。コーチが伝播する回路が生まれない | 一方通行発信ではなく、メンバー間応答の計測 |
| 3 | **入口なき城** | 既にやる気のある人だけが入る「活性化済み限定クラブ」。新規参加が止まり老齢化 | オンボーディング設計、新規参加導線、「初回」シグナル |
| 4 | **リーダー二重負担** | CM 不在でリーダーがビジョン発信と関係維持を兼務、燃え尽きる | 担当割当の明示、ロール分離、業務量の可視化 |
| 5 | **投資の測定錯覚** | リーダー育成は数えられる (研修回数・認定者数) が、CM 仕事は数えられない (防いだ離脱・育てた関係)。測れないから重要でないという錯覚が組織を壊す | **これが本ポータルの存在意義**。CM の仕事を測れる指標を提供する |

## 9. コミュニティ ROI 測定 (2026 CCC Framework) — **指標設計の正本**

CM の仕事を測るための 5 本柱。**本ポータルの KPI ダッシュボードはこれを直接反映する**:

| # | 柱 | コミュニティ内の行動指標 (KPIs/Behaviors) | ビジネス上の測定指標 (Metrics) |
|---|---|---|---|
| 1 | **Retention (定着・維持)** | プラットフォームログイン頻度、Email 開封率・クリック率、セッション滞在時間、ドキュメント DL 数 | CLV、NPS 改善、Churn 低下、オンボーディング成功率 |
| 2 | **Contribution (貢献・活性化)** | Q&A 数、UGC 投稿数、イベント登録、メンバー間 DM/フォロー | イベント収益、平均応答時間短縮、DAU/MAU 比率 |
| 3 | **Support & Efficiency** | ピア・ツー・ピア課題解決数、メンバー主導の回答数、サポートコンテンツ検索数 | 問い合わせ削減数、サポート人件費削減、対応時間削減 |
| 4 | **Growth (成長・獲得)** | 口コミ経由新規、SEO 流入、新規メンバーの初回イベント参加 | 成長率、CPA 改善、口コミ増加 |
| 5 | **Relevance (妥当性・影響力)** | アンケート回答率、議論トピックのトレンド、運営発信へのコメント数 | FB 反映度、業界レポートへの寄与、イベント質的評価 |

### 既存アプリ指標との対応 (重要)
| ポータル評価指標 (前回ユーザー回答) | 2026 CCC Framework |
|---|---|
| ユーザー使用率 (DAU/WAU、画面到達率) | **#1 Retention** + **#2 Contribution の DAU/MAU** |
| バグ報告数 | **#3 Support & Efficiency** の派生 (低いほど Support 効率が高い) |

業務 KPI 側 (顧客企業のヘルス/Churn):
| 既存 | 2026 CCC Framework |
|---|---|
| ヘルススコア (出席・週次・面談) | **#1 Retention** + **#2 Contribution** |
| Churn 率 | **#1 Retention** の負側 |
| 1on1 / 議事録 (※ 1on1 ログ機能は不採用) | **#3 Support** (ピア化を目指す) |
| VoC | **#5 Relevance** |

→ **次フェーズで `lib/domain/health.ts` を CCC Framework 直結で再設計する。** 現行の出席率・週次・面談は #1 Retention の一部に過ぎず、#2-#5 が欠落している。

## 10. AI と CM の役割分担

| AI に任せる | 人 (CM) が担う |
|---|---|
| 非同期タスク / 定型業務の自動化 (集計・請求・タスク生成) | 人間的な共感 (Empathy) と感情的介入 |
| 24h 一次対応 (FAQ チャットボット) | 高度なコンフリクト解決 |
| ホンネ (インサイト) の抽出・分析 (ゼロパーティデータ) | AI のオーケストレーション (設計指揮) |
| ドラフト作成・解決策提案 (案内文・コピー) | 熱狂とカルチャーの醸成 |

→ 本ポータルの AI 機能 (Claude による抽出・要約・ドラフト) はこの分担に従う。**メンバーと話す時間を奪わない方向に AI を使う**。

## 11. コミュニティマネージャーの 6 essential skills

エッセンシャルスキル (+ AI 活用):
- **SPACE MANAGEMENT** — 施設管理・空間デザイン
- **MEMBER MANAGEMENT** — リクルーティング・メンタリング
- **EVENT MANAGEMENT** — 企画・実行
- **MEDIA MANAGEMENT** — 活動の記録・広報・PR
- **PROJECT MANAGEMENT** — 戦略・財務・タスク管理・評価
- **SELF RESOURCE MANAGEMENT** — 自己管理・ネットワーク拡大

→ 本ポータルが直接支援するのは特に **MEMBER / EVENT / PROJECT / MEDIA**。

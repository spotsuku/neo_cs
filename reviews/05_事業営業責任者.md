# CSポータル レビュー — 事業責任者・営業責任者視点

対象: `/Users/furuken/dev/neo_cs/neo-cs-v2/`
レビュー日: 2026-05-03
レビュアー観点: 事業責任者 / 営業責任者（辛口）

---

## 総評

UIとしては「ヘルススコア」「更新ファネル」「研修別カード」など見栄えのするコンポーネントが揃っており、**CSオペレーターが自分の担当を可視化するツール**としては及第点。しかし、**事業/営業を動かすための"通知導線・売上影響の即時把握・営業-CS情報連携・プロダクトフィードバックループ"が壊滅的に欠落**している。

現状のポータルは "見るだけのダッシュボード" であり、「Redになりました」「更新60日前です」と**画面を開いた人にだけ**伝わる仕組みしかない。営業/事業責任者にエスカレーションされる導線、解約による売上インパクトの自動算出、商談履歴・契約条件・受注経緯といった**営業ドメインの情報が一切持ち込まれておらず**、CSが"孤島化"している。報告ツールとしては動くが、**収益を守る/伸ばす道具としては未完成**と評価する。

---

## 致命的問題

### 1. 解約リスクが営業/事業責任者にエスカレーションされる導線が存在しない
- `app/page.tsx:147-200` の「要対応企業」テーブルは画面表示のみ。**Slack/メール/プッシュ通知で営業責任者・事業責任者に届く仕組みがない**。
- `app/notifications/page.tsx:16-29` の通知データもCS担当（古野）視点の単一受信者前提。**「Redに変化→営業マネージャ→事業責任者」というエスカレーション階層の概念が型レベルにない**（`Notification` 型にrecipient/severity/escalation_level がない）。
- `lib/mock/churn.ts:17` の `notified: boolean` は単一フラグで「誰に通知したか」「未通知ならいつ誰に上げるか」が表現できていない。**SLA超過時の自動エスカレーションが設計されていない。**

### 2. 売上影響の即時把握が極めて弱い — 「いくら失うか」が一目で見えない
- `app/page.tsx:147` のAt-Riskテーブルに**MRR/ARR列がない**。Red企業が並んでいても "失う売上" が分からない。
- `lib/mock/data.ts:327` 付近の `alerts` データに金額情報なし（`reason` `daysSinceLastTouch` のみ）。経営判断には不十分。
- `components/RenewalFunnel.tsx:11-26` で MRR合計は表示されるが、**「At Risk が全部解約したら年商△万円」「コミット率×金額の確度別予測」が出ない**。フォーキャスト機能ゼロ。
- `snapshot.atRiskCount` (`lib/mock/data.ts:139`) は社数のみ。**At-Risk MRR / At-Risk ARR がKPIに無い**のは事業責任者として致命的。

### 3. アップセル・クロスセル機会の検知が皆無
- 4研修（academia/hyogikai/aiken/commu）を持っているのに、**「academiaしか契約していない好調Green企業」=クロスセル候補のリストが存在しない**。
- `lib/mock/cycles.ts:44` で `JourneyStage` に `expansion` が定義されているが、**expansion stage企業を抽出して営業に引き渡すUIがどこにもない**（grep結果でも `expansion` を使ったページは0）。
- `ContinuousProductCard.tsx` `OneShotProductCard.tsx` は研修単体KPIしか出さず、**「現受講者の他研修クロス率」「リピート見込み顧客」が表示されない**。
- `OneShotProductCard.tsx:80` の "リピート率" は集計値のみで、**個社×次回開講のレコメンドリスト**が無い。AIKEN受講後にacademiaへ誘導する設計が皆無。

### 4. 営業-CSの情報連携 — 商談履歴・契約条件・受注経緯が完全欠落
- `lib/mock/contracts.ts:26-45` の `Contract` 型に**商談履歴（dealId）・受注決め手・割引条件・契約特記事項・営業担当者・SFAリンクが無い**。`ownerName` 一個では誰がCS・誰が営業か判別不能。
- `app/companies/[id]/CompanyDetail.tsx` のタブ構成 (line 61-70) は `overview/weekly/contracts/logs/onboarding/surveys/engagement/mail` で、**「商談履歴」「受注時の約束事項」タブが無い**。CSが「なんでこの値段で売ったの?」「どんな約束で受注したの?」を確認できない。
- `app/companies/new/page.tsx:166` で「営業担当者」欄はあるが、CS担当との二重管理・引き継ぎワークフローが設計されていない。

### 5. 受注後の引き継ぎ品質 — handoff statusが定義だけで運用導線なし
- `lib/mock/contracts.ts:7` で `handoff` ステータスが定義され、`onboarding.ts:447` 等で「handoffはオンボから除外」と扱われているが、**handoff専用の引き継ぎチェックリスト・引き継ぎMTGログ・営業→CSの申し送りメモ機能が実装されていない**。
- 受注時の前提（KPI合意・成功定義・社内キーパーソン構造）がCSに伝わる構造化された場所が無い。`SuccessPlan` (`cycles.ts`) は存在するが、**営業時点の「お客様の本当の課題」「決裁プロセス」「競合状況」が紐づかない**。

### 6. プロダクト改善へのフィードバックループが事実上存在しない
- アンケート (`surveys.ts`) や週次レビューの自由記述は溜まるが、**「プロダクト課題タグ」「機能要望集約ビュー」「研修コンテンツ改善提案ダッシュボード」が無い**。
- grep で `feedback` は単発のメール本文に出てくるだけ（`email.ts:113, 219, 469`）。**VOC→プロダクト/コンテンツ責任者への定常的なルーティング設計が無い**。
- 解約理由 `churn.ts:7-14` のカテゴリは6種だが、**「value_unfit」「low_engagement」が積み上がってもプロダクト/コンテンツ改善KPIに接続されない**。学びがプロダクトに還流しない。

## 重要な懸念

### 7. 顧客セグメント別の状況把握が貧弱
- `entities.ts:10` に `industry` はあるが、**従業員規模・売上規模・契約金額帯（Tier）・LTV/ARPAなどセグメント軸が無い**。「金融セグメントのRed率」「大企業/中堅のChurn差分」が出せない。
- `app/companies/page.tsx` のフィルタは Health/Product/Owner/業種検索のみ。**Tier別（Enterprise/Mid/SMB）、契約期間別、初回vs更新後のセグメント分析ができない**。
- 研修別カード (`ContinuousProductCard.tsx`) は集約値のみで、**業種クロス・規模クロスが取れない**。

### 8. NRR/Churn/MRRの分解が表面的
- `MrrSparkline.tsx` は単純な折れ線。**New MRR / Expansion / Contraction / Churn の Waterfall が無い**。事業責任者が「今月のMRR増加の中身」を判断できない。
- `continuousSummary.nrr` (`ContinuousProductCard.tsx:54-60`) はあるが**算出根拠（GRR/Logo Churn/Revenue Churn）が画面で示されない**。数字を信じる根拠が無い。
- `reports/page.tsx:43-51` の「MRR推移詳細」テンプレが**未実装（モック）**。経営報告に直結する一番重要なレポートが空。

### 9. 更新確度（Committed/Likely/At Risk）の判定根拠がブラックボックス
- `RenewalFunnel.tsx:30-46` でステージ別MRRは出るが、**「なぜCommitted扱いか」「Likely→At Risk転落の理由」がCS担当の主観入力か機械判定か不明**。
- `lib/mock/contracts.ts` では `renewalStatus` から派生させているだけ (`deriveHealthScore`)。**判定アルゴリズムの透明性が無く、営業会議で議論できない**。

### 10. 契約終了後のクロージング・ウィン/ロス分析が薄い
- `churn.ts:38-57` で再アプローチ予定は持つが、**Win/Loss理由の構造化分析（競合別・価格帯別・業種別の解約率）ダッシュボードが無い**。
- `RenewalView.tsx:295-403` の「再アプローチ」タブも**個別レコード一覧のみ**で、トレンド/学びを集約できない。

### 11. 通知のリアルタイム性とアクション完了管理
- `notifications/page.tsx` は静的配列。**実際のSlack連携/メール連携は実装プランも見えない**。
- 通知に対する「対応した/しない」のSLAタイマーが無い → 通知が放置されても誰も気付かない。

## 評価できる点

- **更新ファネル概念の導入** (`RenewalFunnel.tsx`)：Committed/Likely/At Riskで金額付きで切る設計は良い土台。あとはWin確度×金額の重み付けと、ステージ移動の通知さえ加わればパイプラインツールに化ける。
- **At-Risk企業の「AI推奨アクション」列** (`app/page.tsx:163`)：示唆がテーブルに載るのは攻めた良いUI。実データで実用化できれば営業の判断速度が上がる。
- **研修別ヘルス分布** (`HealthSection.tsx:79-110`)：複数選択可・全体トグル可の作りは事業責任者が「どの研修が痛んでいるか」を瞬時に把握できる良UX。
- **解約レコードの再アプローチ予定管理** (`churn.ts` + `RenewalView.tsx:295-`)：解約=終わりではなく次の商談ネタとして残す思想は◎。営業引き渡し導線まで作れば武器になる。
- **AccountJourney に `expansion` ステージ定義** (`cycles.ts:44-53`)：拡大フェーズを概念上は持っているのは将来性あり。
- **継続/単発の分離設計** (`ContinuousProductCard.tsx` / `OneShotProductCard.tsx`)：プロダクト特性に合わせKPIを分けたのは事業判断に資する。

### 優先度 S（事業継続のため即時着手）

1. **At-Risk MRR/ARRをトップKPIに昇格**
   - `snapshot` (`lib/mock/data.ts:133-`) に `atRiskMrr` `atRiskArr` `forecastedChurnMrrNext90d` を追加し、`app/page.tsx:69-74` の KpiCard を「At-Risk企業 7社 / **失う見込みMRR ¥X万**」に変更。
   - `alerts` (`data.ts:327`) の各レコードに `mrr` `endDate` `churnImpactScenario` を追加し、`app/page.tsx:154-198` のテーブルに**MRR列・ARR影響列**を追加。

2. **エスカレーション通知の階層設計**
   - `Notification` 型に `recipientRoles: ("cs"|"sales_lead"|"exec")[]` `severity` `escalationLevel` `slaDeadline` を追加。
   - Red化検知 → 24h無対応 → 営業マネージャ通知 → 72h無対応 → 事業責任者通知、というSLAエスカレーションを実装。Slack Webhook前提で設計を固める。

3. **解約→売上影響シミュレーション**
   - `RenewalFunnel.tsx` に「At Risk全件解約時のMRRインパクト」「確度重み付け予測MRR (Committed×95% + Likely×60% + AtRisk×20%)」を追加。

### 優先度 A（四半期内）

4. **アップセル/クロスセル候補リストの新規ページ**

## 結論（事業責任者として）

「綺麗なCSダッシュボード」としては及第点だが、**売上を守り・伸ばすための仕組みとしては根本的に弱い**。特に「At-Risk MRRの即時可視化」「営業/事業へのエスカレーション通知」「アップセル候補の営業引き渡し」「商談履歴のCS取り込み」の4点は **次フェーズ最優先で実装しないと、ポータルが"監視塔"のまま"司令塔"にならない**。CS単独ツールから**事業オペレーティングシステム**へ脱皮することを強く推奨する。

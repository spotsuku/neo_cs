# 12. 他部署連携レビュー（営業・マーケ・開発の責任者視点）

レビュー対象: `/Users/furuken/dev/neo_cs/neo-cs-v2/`
レビュー日: 2026-05-03
レビュアー視点: 「CSとは連携必須。だがこのアプリを毎日触るつもりはない」他部署マネージャー

---

## 総評

率直に言って、これは「CS部門の中だけで閉じたツール」だ。Slack/Gmailの**通知パイプ**は太く敷かれているが、営業・マーケ・開発の責任者が「自分の業務文脈に持ち帰れる導線」がほぼ無い。CRM（Salesforce/HubSpot）連携、Notion/タスクツール連携、公開Web API、Webhook、読み取り専用の他部署ロール、いずれも実装どころか設定画面の**選択肢にすら存在しない**（`app/settings/page.tsx:13-43` のメニューは「研修マスタ／ユーザー／Gmail／通知」の4つだけ）。

CSが集めた一次情報（顧客の声・ネガティブシグナル・更新シグナル）は、AI抽出までは光るが、その後の「営業の商談履歴に紐づく」「マーケの事例化キューに入る」「開発のIssueトラッカーに転送される」といったハンドオフが全て**人手のSlack転記頼み**。これは中規模を超えた瞬間に破綻する設計だ。

二重入力リスクも高い。営業の商談データ（CRM）とCSの企業カルテ（`app/companies/`）が独立して存在しており、コンタクト・契約・担当者を**両方で別管理する未来**が見える。

---

## 致命的問題

### 1. CRM/SFA連携がゼロ — 営業との情報分断が確定している
- `app/settings/page.tsx:13-43` の連携メニューに **Salesforce / HubSpot / Zoho などCRMが一切無い**。
- `app/companies/[id]/CompanyDetail.tsx:59-70` のタブ構成（概要／週次／契約／面談ログ／オンボ／…）は完全にCS閉域で、「商談履歴」「失注理由」「初期提案資料」へのリンクが無い。
- 結果として、営業が握る「なぜこの顧客が入ったか・初期期待値」と、CSが握る「実際どう使われているか」が**分断される**。アップセル/クロスセル時に営業がCSポータルを見る動機もないし、見てもアクション導線が無い。

### 2. 公開API / Webhookが未提供
- `api/claude.js:1-39`, `api/auth.js:1-80` を見るに、バックエンドAPIは「Anthropic呼び出しプロキシ」と「Google OAuth＋ユーザー管理」のみ。**外部システムに対するREST/GraphQL APIや、イベントを発火するWebhook機構は存在しない**。
- `Access-Control-Allow-Origin: '*'` (`api/claude.js:4`, `api/auth.js:14`) が雑に開いている割に、肝心の業務データ（companies/contracts/voc）へのAPIエンドポイントは無い。これではマーケ部のBI（Looker/Tableau）にも繋げられない。
- データ可搬性は `app/reports/page.tsx:24-79` のPDF/Excel/CSV手動エクスポートのみ。**スケジュール配信もAPI経由取得もできず、毎月人がボタンを押す前提**。

### 3. 顧客の声（VOC）→ 開発への導線が設計されていない
- `app/inbox/InboxView.tsx:35-48` の AI抽出タイプは `onboarding_task_done / stakeholder_change / negative_signal / next_action / renewal_signal` の5種だけで、**「プロダクト要望（feature_request）」「不具合報告（bug_report）」が抽出カテゴリに無い**。
- 通知ルール `app/settings/notifications/page.tsx:13-70` を見ても、宛先は全て `cs-*@neoacademia.jp` または `#cs-*` チャンネルで、**開発チーム（#dev / GitHub / Linear / Jira）への転送ルールが0件**。
- 結果、顧客から上がった「この機能が欲しい」がCSのメモに沈み、開発バックログに届かない。プロダクトマネージャーとして看過できない。

### 4. マーケへの成功事例還元が無い
- `app/reports/page.tsx:24-79` の6テンプレートは全て「経営／更新／At-Risk」向けで、**「成功事例（カスタマーサクセスストーリー）」「ロゴ使用許諾済みリスト」「NPS高評価コメント抽出」のような、マーケが事例コンテンツに使えるアウトプットが無い**。
- `surveys` データ（`lib/mock/surveys.ts`）に良いコメントが眠っているはずだが、マーケがアクセスする導線・通知が定義されていない。

## 重要な懸念

### 5. 他部署向けの「読み取り専用」ロール設計が貧弱
- `app/settings/users/page.tsx:109-131` で `Admin / CS / 閲覧` の3ロール。一見、閲覧ロールがあるが「**全データ閲覧可能**」(`page.tsx:128`) と粗い。営業に渡せば他社の解約理由まで丸見え、開発に渡せば契約金額まで丸見え。
- 「自分が関係する企業のみ閲覧」「VOCだけ閲覧」「事例化候補だけ閲覧」のような**部分閲覧ロール（scoped viewer）が存在しない**ため、結局「Slackで貼ってもらう」運用に逆戻りする。
- 認証もGoogle OAuthのみ（`api/auth.js:29-55`）でSSO/SCIM等の話が無く、IT部門としても他部署アカウント発行の運用負荷が読めない。

### 6. 商談↔CS活動の相互参照リンクが無い
- `CompanyDetail.tsx` で表示される企業カルテに「商談ID」「Salesforce URL」のような外部キーフィールドが見当たらない（`lib/mock/entities` 由来のCompany型に依存）。
- 営業から見ると「自分の商談画面からワンクリックでCS活動が見える」が無く、CSから見ると「初期商談時の議事録・提案書」が見られない。**双方向リンクの欠落**は、組織が大きくなるほど致命傷になる。

### 7. Gmail連携が「メール一方向取り込み」止まり
- `app/settings/gmail/page.tsx:79-279` 全体を通して、Gmail連携は「受信メールを取り込み、AIで要約」のみ。**「CSポータルからGmailにスレッドリンクで戻る」「営業の元メール（CC履歴）を辿る」が想定されていない**。
- また `targetLabels` (`gmail/page.tsx:11-17`) は CS用ラベル前提で、`営業`, `マーケ`, `セールス` のラベル別取り込みフィルタに関する設計思想が見えない。「CSメールアドレスにforwardしてもらう運用」に依存している匂いがある。

### 8. Slack通知が"CS内向け"に閉じている
- `app/settings/notifications/page.tsx:13-70` の7ルール、Slackチャンネルは `#cs-alerts / #cs-weekly / #cs-renewal / #cs-onboarding / #cs-inbox / #cs-meeting / #cs-general`、メール宛先も全て `cs-*@`, `renewal@`, `support@`。
- 「**契約更新60日前**」(`r3`) は本来、営業マネージャーや経営にも自動通知すべきだが、現状は `#cs-renewal` と `renewal@` のみ。アップセル提案のタイミングを逃す。
- 「**VOC緊急タグ**」(`r7`) も `#cs-alerts` のみで、開発・PdMに飛ばないとプロダクト改善に繋がらない。
- 通知抑制の粒度（`page.tsx:289-298`）は「ユーザー個別ではなく全体一律」しか無く、他部署を巻き込んだ瞬間「うるさいから全部ミュート」される未来。

### 9. AI抽出の承認フローがCS担当のみ
- `InboxView.tsx:418-432` の承認/却下ボタンは画面に直結。**他部署からのレビュー（"これマーケ事例にしていい？" "開発バックログに上げるべき？"）の介在ポイントが無い**。
- pending件数バッジ（`InboxView.tsx:152-153`）はCSの作業キューになっており、件数が溜まるほど他部署視点のシグナルが埋もれる。

### 10. APIキーの取り扱いとログが粗い
- `api/claude.js:36-37` でエラーは `console.error` で吐くだけ、`api/auth.js` 同様。SOC/監査の観点で他部署（特に情シス）に説明できない。
- `Access-Control-Allow-Origin: '*'` (`api/claude.js:4`, `api/auth.js:14`) は社内IDPの観点で要修正。

## 評価できる点

- `app/inbox/InboxView.tsx:91-119` のSLA超過バッジ・ステータス／担当の即時編集はCSオペレーション品質として高水準。他部署が「いつまでに対応されるか」をリンクで覗けるなら価値が出る。
- `app/inbox/extractions/` のAI抽出を**承認制**にしている (`InboxView.tsx:418-437`) のは、AI誤検知が他部署に伝播するのを防ぐ良い設計。ここに「マーケ転送」「開発転送」のアクションを足す余地は大きい。
- `app/reports/page.tsx:24-79` の定型レポートに「経営向けKPIサマリー」「At-Risk」「更新パイプライン」といった**部署横断で意味があるテンプレート**が並んでいる点は評価できる。あとは自動配信化すればよい。
- `app/settings/notifications/page.tsx:188-256` の通知ルールがテーブル構造で拡張前提。チャンネルとメール宛先を**ルール単位で**指定できるので、他部署宛先の追加自体はUI改修だけで済む。
- `api/auth.js:96-112` で「最初のユーザーは自動Admin」など現実的な初期化フロー。

## 改善提案

### 即時（1〜2スプリント）

1. **通知ルールに `部署宛先` を追加**: `app/settings/notifications/page.tsx:13-70` の各ルールに「営業マネージャー」「PdM」「マーケ」へのSlack/メール宛先を追加。特に `r3` 更新60日前 → 営業、 `r7` VOC緊急 → 開発（`#dev-voice` + GitHub Issue自動起票）。
2. **AI抽出タイプに `feature_request` `bug_report` を追加**: `app/inbox/InboxView.tsx:35-48` の `AiExtractionType` を拡張。承認時に「開発に転送」アクションを追加（Linear/Jira/GitHub Webhook）。
3. **閲覧ロールを `scoped_viewer` に分割**: `app/settings/users/page.tsx:109-131` を `Sales-Viewer / Marketing-Viewer / Dev-Viewer` に分け、閲覧範囲（金額マスク／顧客名マスク／VOCのみ等）を定義。

### 中期（1四半期）

4. **公開REST API + Webhook基盤**: `api/` 配下に `/api/companies`, `/api/voc`, `/api/contracts` のGETを追加し、APIキー発行UIを `app/settings/` に。同時に `event=health.changed`, `event=voc.urgent` 等のWebhook送出を実装。
5. **CRM双方向同期**: `app/companies/[id]/CompanyDetail.tsx` のCompany型に `crmId / crmUrl` を追加し、商談履歴タブを設置。SalesforceまたはHubSpotとの夜間同期＋Webhook受信。
6. **マーケ向け「事例候補」ビュー**: `app/reports/page.tsx` のテンプレートに「事例化候補（NPS9-10＋ロゴ許諾済み）」を追加、マーケのSlack `#mkt-case-bank` に週次自動配信。

### 長期

7. **全社的な"顧客プロフィール"の単一ソース化**: companies を全社マスタに格上げし、CS/営業/マーケ/サポートが**部分ビュー**で参照する設計へ移行。CRMをマスタにしてCSポータルがビューになるパターンも要検討。
8. **CORSと監査ログの整備**: `api/*.js` の `Access-Control-Allow-Origin: '*'` を社内ドメインに限定し、操作ログを別テーブル化（情シス/SOC2対応）。

---

**結論: CS部門単体の生産性ツールとしては良いが、"全社の顧客理解インフラ"には程遠い。** 他部署責任者として、現状ではこのアプリを自部門のメンバーに「使え」とは言えない。最低でも上記1〜3を優先実装してほしい。

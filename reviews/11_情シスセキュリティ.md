# 情シス／セキュリティ責任者レビュー — neo_cs CSポータル

レビュー日: 2026-05-03
レビュー対象: `/Users/furuken/dev/neo_cs`
レビュアー視点: 情報システム部門責任者 / CISO

---

## 総評

結論から言えば、**現状の neo_cs を「社内CSポータル」として本番稼働させることはセキュリティ上認可できない**。最大の問題は以下3点に凝縮される。

1. **RLS が `for all using (true)`**（`supabase_schema.sql:29-30`）でanonキー直撃の全件 R/W が可能。
2. **API群（`api/db.js`, `api/db-all.js`, `api/claude.js`）に認証チェックが一切無い**。`/api/db` を curl で叩けば誰でも `ps_data` を読み書き・削除できる。
3. **CORS が全API `Access-Control-Allow-Origin: *`**（`api/auth.js:14`, `api/db.js:11`, `api/db-all.js:9`, `api/claude.js:4`）。社内ポータルでこれは論外。

加えて、新フロント（`neo-cs-v2/`）側は **設定画面が全てモックの静的JSX**（`app/settings/users/page.tsx:16-107` に氏名・メール・最終ログインがハードコード）で、認証・権限判定・監査ログが**コードとして1行も実装されていない**。「Admin/CS/閲覧」のロール表示はあるが、それを enforce する処理はバックエンドにもフロントにも存在しない。経営者レビュー（01）が指摘した「フロントとバックが別アプリ」状態は、セキュリティ観点でも致命傷になっている。

Next.js 16 への更新は評価できるが、それは**前提**であって対策ではない。本ドキュメントでは「これを直さないと顧客データを置いてはならない」項目を列挙する。

## 致命的問題

### 1. Supabase RLS が完全無効と等価（`supabase_schema.sql:25-30`）

```sql
alter table ps_data enable row level security;
create policy "allow_all" on ps_data for all using (true) with check (true);
```

- `enable row level security` を入れているが直後に `using (true) with check (true)` の全許可ポリシーを貼っており、**RLSを有効化した意味が完全に消えている**。
- しかも `ps_data(key text, value jsonb)` の単一テーブルに**全てのデータ（企業情報・面談ログ・アクション・契約状況など）を放り込む設計**（`api/db.js:38-45`, `api/db-all.js:23`）。1ポリシーで全顧客情報が露出する構造。
- Supabase の **anon key を `Authorization: Bearer` でそのまま使っている**（`api/db.js:103-104`, `api/db-all.js:38-39`, `api/auth.js:134-135`）。anon key はクライアントに渡る前提のキーだが、ここではサーバ経由で全件アクセスに使われており、service_role でなくても全件を取れる/書ける状態。
- RLS が事実上無効なので、**Supabase ダッシュボードURL と anon key が漏れた瞬間に全顧客データが流出**する。

### 2. `/api/db`, `/api/db/all`, `/api/claude` に認証が一切ない

- `api/db.js:10-30` には `body` を JSON パースしてそのまま Supabase に転送する処理しかない。**呼び出し元のユーザー識別もセッション検証もゼロ**。
- `api/db.js:50-58` の delete アクションも認証なし。匿名で `{action:'del', key:'meetings_1'}` を投げれば任意レコードが消せる。
- `api/db-all.js:23` は GET 一発で全件返す。社内全企業の機微情報を**未認証で取得可能**。
- `api/claude.js` は **誰でも呼べる Anthropic API のプロキシ**になっており、第三者にスクレイピングされれば**ANTHROPIC_API_KEY の課金が無制限に消費**される（レート制限・origin制限・トークン制限なし）。
- `server.js:56-66` で `/api/claude` を生 Node HTTP に直結しており、**リクエストサイズ上限すら無い**。巨大ボディで OOM 攻撃可能。

### 3. CORS が全API 全オリジン許可

`api/auth.js:14`, `api/db.js:11`, `api/db-all.js:9`, `api/claude.js:4` 全て：

```js
res.setHeader('Access-Control-Allow-Origin', '*');
```

社内向けの個人情報を扱うAPIで全オリジン許可は **OWASP API Security Top 10 (API8:2023 Security Misconfiguration)** に直接該当。攻撃者の用意した HTML から `fetch('/api/db', {method:'POST', body:JSON.stringify({action:'all'})})` で全件抜き取れる。CSRF対策（同一オリジン制約）の最後の砦すら自ら外している。

### 4. 認可ロジックがリクエストボディの自己申告に依存（`api/auth.js:58-77`）

```js
if (action === 'users') {
  const { email } = body;
  const requester = await getUserByEmail(email);
  if (!requester || requester.role !== 'admin') { ... }
```

- **「自分が誰か」をクライアントが body に書いて送る方式**。`{action:'setRole', email:'admin@company.jp', targetEmail:'attacker@x.com', role:'admin'}` を投げるだけで、admin の email を1つ知っていれば任意ユーザーを admin に昇格できる。
- Google ID トークンの検証（`api/auth.js:82-94` の `googleVerify`）はログイン時の `verify` でのみ実行され、**それ以降のリクエストはトークン検証を一切しない**。セッション概念が無い。
- `verify` の結果は `res.status(200).json({user:{...role}})` でクライアントに返すだけ（`auth.js:41-50`）。Cookie もJWT も発行していないため、クライアントが localStorage に保存した `role` を改ざんしても検知不能。

### 5. 「最初のユーザーは自動 admin」（`api/auth.js:105-107`）

```js
const allUsers = await getAllUsers();
const role = allUsers.length === 0 ? 'admin' : 'member';
```

`/api/auth` が無認可で叩ける状態と組み合わさると、**デプロイ直後のレースで先に `verify` した外部の Google アカウントが admin を奪取**する。CTF レベルの攻撃面。

### 6. `index.html` の生 DOM 構築による XSS リスク（旧フロント）

- `index.html:676, 882, 1268, 1464, 1478, 1507-1509, 1517-1518, 2115` 等で `innerHTML = ...` にユーザー入力（企業名・面談メモ・アクションテキスト）を**エスケープ無しで埋め込み**。
- 例: `index.html:1507` の `addAction` は `text=document.getElementById(...).value.trim()` を `LS.setArr` 経由で保存し、`renderActions(no)` の戻り値を `innerHTML` に入れている。`<img src=x onerror=alert(document.cookie)>` を仕込めば永続XSS。
- localStorage に保存→Supabase に同期される（`api/db.js`）ため、**1人が仕込めば全社員の画面で発火する Stored XSS**。
- `server.js` 配信に CSP / X-Frame-Options / X-Content-Type-Options のヘッダが**1つもない**（`server.js:81-91`）。

### 7. `.env` 取り扱いとシークレット管理

- ルート `.gitignore` に `.env` `.env.local` はある（OK）が、**手書きの簡易 dotenv パーサ**（`server.js:14-25`）は `=` を含む値や複数行値を正しく扱えず、`KEY=foo=bar` を `process.env[KEY]='foo=bar'` にする実装なのは偶然動いているだけ。シークレット管理は Vercel/Supabase の env か Secret Manager に寄せるべき。
- `api/claude.js:36-37`, `api/db.js:82-83`, `api/auth.js:52-53` で **エラー文字列をクライアントにそのまま返している**。Supabase のスキーマ名・401 詳細・Anthropic エラーが漏れる。情報窃取の足掛かり。
- `console.error` ログは Vercel ファンクションログに出るのみで、**API key の prefix が混入する事故が起きても気づけない**監視体制。

## 重要な懸念

### 8. 監査ログがゼロ

- `neo_users` テーブルに `last_login` だけはあるらしい（`api/auth.js:101`）が、**「誰がいつどのレコードを編集/削除したか」を記録するテーブル・コードが一切ない**。
- `api/db.js` の保存・削除処理（`50-83`）は actor を取らない、そもそも認証してないので取りようがない。
- 顧客情報を扱う以上、**個人情報保護法の安全管理措置（技術的安全管理措置・アクセス記録）を満たしていない**。社外監査・ISMS いずれも通らない。

### 9. RBAC が「画面ラベルだけ」（`app/settings/users/page.tsx`）

- `app/settings/users/page.tsx:16-107` のユーザー一覧は **静的配列のハードコード**。実在ユーザーの氏名・メール・最終ログインを**コミット済みソースに直書き**しており、リポジトリが漏れれば情報漏洩。
- `app/settings/users/page.tsx:115-131` の roles 定義もただの表示用。`app/settings/users/page.tsx:249-254` の「編集」「削除」ボタンは `href="#"` でロジック未実装。
- Next.js 側の任意ページ（`app/companies/`, `app/weekly/` 等）に**ロールガードのミドルウェアが存在しない**。`middleware.ts` も無いはず。誰でも全ページ閲覧可能。

### 10. 退職者アクセス遮断の手段がない

- `api/auth.js` のユーザー一覧・ロール変更はあるが、**「無効化」「ロック」フラグが neo_users スキーマに無い**（コード上 `role` だけ操作）。退職者の Google アカウントが残っている限りログインし放題。
- セッション失効の概念が無い（前述）ため、「退職処理＝Workspaceで Google アカウント停止」にしか頼れない。情シス運用としてはギリギリ通るが、**同名アカウント再作成や個人 Gmail 経由の不正検知**は不可能。

### 11. データバックアップ・暗号化方針が未定義

- Supabase の自動バックアップ依存（無料/Proで保持期間が違う）について、リポジトリ内に運用ドキュメントなし。
- アプリ層の暗号化は無し。`value jsonb` に PII を平文格納（`supabase_schema.sql:5-10`）。Supabase は at-rest 暗号化されているが、**鍵管理は Supabase 側に依存**。漏洩時の責任分界が曖昧。
- `index.html` 経由で localStorage に**全顧客データのキャッシュが残る**設計（`api/db-all.js` で全件取って LS 同期）。共有PC・盗難端末で即漏洩。

### 12. Next.js 16 / 依存パッケージ

- `neo-cs-v2/package.json` の依存は `next ^16.2.4`, `react ^19.0.0`, `tailwindcss ^3.4.17` のみで非常に薄い。脆弱性面の表面積は小さい（評価点）。
- ただし**ルート `package.json` にロックファイルが無く** (`scripts:{start:"node server.js"}` のみ、依存はゼロ宣言)、`https` は Node 標準なので問題ないが、**SCA（Snyk/Dependabot/`npm audit`）の運用が CI に組み込まれていない**。
- `engines.node:">=18.0.0"` だが Node 18 は 2025-04 EOL。**サポート切れランタイム許容**は情シス的にNG。

### 13. CSRF / セッション固定

- セッション Cookie を発行していないので「CSRF対策が無い」のではなく**CSRF以前に認証が無い**。Cookie 認証を導入する際は SameSite=Lax + CSRF token 必須。
- Google ID トークンを毎回 body で送る方式を続ける場合でも、**トークンの aud（client_id）検証**を `googleVerify`（`api/auth.js:82-94`）で**やっていない**。他サービスの ID トークンを流用される可能性。

### 14. SQLi・パスインジェクション

- Supabase REST 経由なので生 SQL は無いが、**`encodeURIComponent(email)` のみで PostgREST の filter (`?email=eq.${...}`) に埋めている**（`api/auth.js:100, 115, 125`）。コンマや `or=` の混入で**PostgREST フィルタインジェクション**が成立する可能性（例: `email=eq.x@y.com&role=eq.admin` 等が混ぜられる）。
- `server.js:77` のパストラバーサルチェックは `filePath.startsWith(__dirname)` のみ。`path.normalize` を通していないため、シンボリックリンクや Windows 区切り文字、`%2e%2e` の二重エンコードに弱い。今は Unix デプロイ前提でセーフだが脆い。

### 15. IDOR

- `api/db.js` は `key` をそのまま受け取って Supabase に投げる。`meetings_1`, `actions_42` など**会社番号が含まれた key 命名**だが、認証もスコープチェックもないので**他社のレコード key を推測すれば誰でも読める**典型的 IDOR。

## 評価できる点

- `.gitignore` に `.env` `.env.local` `node_modules` `.next` `*.log` が入っており、**シークレットの誤コミットは現時点で発生していない**（`/Users/furuken/dev/neo_cs/.gitignore`, `neo-cs-v2/.gitignore`）。
- Google OAuth で社内 Google Workspace 認証に寄せようとしている方向性は正しい（`api/auth.js:29-55`）。あとは ID トークン検証の aud / hd（hosted domain）チェックを足せば社外締め出しは実現できる。
- Next.js 16 への追従が早い（直近コミット `de49b2a`）。脆弱性アドバイザリ追従の意識はある。
- `server.js:77` のパストラバーサル try は最小限ながら入っている（穴はあるが意識はある）。
- `lib/mock/*.ts` がモックである旨は明確で、**実顧客情報をリポジトリにコミットしてはいない**（`app/settings/users/page.tsx` の社員氏名・メールを除く）。
- CORS や RLS の設定箇所が全てコード／SQL に集約されており、**修正コストは低い**。設計を直す決断さえすれば1スプリントで底上げ可能。

## 改善提案（優先度順）

### P0（本番投入前 必須）

1. **RLS を本物にする**: `supabase_schema.sql:29-30` の `allow_all` を破棄。`auth.uid()` ベースのポリシー（自社 Workspace ドメイン限定 + ロール別）に書き換え。
2. **anon key の用途分離**: ブラウザ用 anon と、サーバ専用 service_role を分け、`api/*.js` は service_role を Vercel 環境変数で持つ。anon key はクライアントには出さない。
3. **API 全件に認証ミドルウェア**: Google ID トークンを毎回 `Authorization: Bearer` で受け取り、`googleVerify` で検証 → Supabase の `neo_users` と突き合わせ → role を**サーバ側で決定**。`body.email` で role を判定する箇所（`api/auth.js:59-75`）を全廃。
4. **CORS をホワイトリスト化**: `Access-Control-Allow-Origin: *` を 4 ファイル全て削除し、`https://cs.neoacademia.jp` 等の固定値に。
5. **Stored XSS 排除**: `index.html` の `innerHTML` 全箇所をテンプレートリテラルから DOM API（`textContent` / `createElement`）に置換、もしくは旧 `index.html` を完全廃止して Next.js v2 に一本化（経営者レビュー01の提言と同じ結論）。
6. **`/api/claude` のレート/サイズ制限**: 認証必須化 + IP/ユーザー単位レート + max body 32KB + max_tokens 上限固定。Anthropic キー流用を防ぐ。

### P1（90日以内）

7. **監査ログテーブル追加**: `audit_logs(actor_email, action, target_key, before, after, ip, ua, ts)` を作り、`api/db.js` の write/delete を全て記録。
8. **`neo_users` に `is_active`, `disabled_at`, `last_seen_ip` カラム追加**: 退職者は role 変更ではなく is_active=false で即遮断。Workspace 連携で自動同期するスクリプトも検討。
9. **CSP / セキュリティヘッダ**: `server.js` のレスポンスヘッダ（または `next.config.mjs` の `headers()`）に CSP, HSTS, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy を必須化。
10. **`googleVerify` の aud / hd 検証**: `api/auth.js:82-94` で `info.aud === GOOGLE_CLIENT_ID && info.hd === 'neoacademia.jp'` を確認。社外 Google アカウント締め出し。
11. **エラー応答のサニタイズ**: `e.message` をそのまま返さず、内部ログには詳細・クライアントには `{ code: 'INTERNAL' }` のみ返す。
12. **`app/settings/users/page.tsx` のハードコード削除**: 実在社員の氏名・メール・最終ログインをソースから除去し、Supabase の `neo_users` を fetch する実装に。

### P2（運用整備）

13. **依存パッケージ脆弱性管理**: GitHub Dependabot 有効化 + 月次 `npm audit` を CI 必須化。Node ランタイムを 20 LTS 以上に。
14. **バックアップポリシー**: Supabase Pro 以上で日次 PITR 有効化、30日保持。リストア手順を README に明記。月次でリストア訓練。
15. **データ暗号化**: 機微フィールド（顧客個人名・連絡先）はアプリ層で envelope 暗号化（KMS 鍵管理）。`ps_data.value jsonb` のスキーマも正規化分割（経営者レビュー01のP2と統合）。
16. **localStorage キャッシュの最小化**: 全件キャッシュをやめ、必要な企業のみオンデマンド取得。離席ロック・ブラウザ閉鎖時クリアを検討。
17. **侵入検知**: Supabase の Logs を Datadog/CloudWatch 等に送り、`ps_data` への `select=*&limit=1000` を超える参照、深夜帯の大量 read、未知 IP からの login を検知ルール化。
18. **ペネトレーションテスト**: 上記 P0/P1 完了後、外部ベンダーで脆弱性診断（OWASP Top 10 + API Security Top 10）。年1回継続。

## 結論

「**現時点で社内CSポータルとして稼働させてはならない**」が情シス・セキュリティ責任者としての判断。
特に `supabase_schema.sql:29-30` の RLS無効ポリシーと、API群の無認証 + CORS全許可の組み合わせは、**1日で全顧客データ流出が成立する状態**。Next.js 16 への更新や Google OAuth の骨格はあるが、**実装の95%はUIモックであり、セキュリティ機能は未着手**と言って差し支えない。

P0 を完了するまで、本番ドメインへの公開・実顧客データの投入を**一切認可しない**。

## 総評

率直に言って、これは**「BIで分析できる業務システム」ではなく、「画面に表示するためのJSON置き場」**です。Supabaseスキーマは事実上1テーブル（`ps_data(key, value jsonb)`）のKVSであり、リレーショナルDBの強みを完全に放棄しています。フロント側のデータモデル（`lib/mock/*.ts`）は型の上では精緻に見えますが、**ヘルススコア・解約率・更新率・NRRといった主要メトリクスの算出ロジックがどこにも実装されておらず、すべてハードコード**された数値を画面に流し込んでいるだけ。コホート分析、ファネルの実イベント追跡、解約予測のいずれも現状では**不可能**です。MVPとしては許容できますが、「データドリブン」を標榜する瞬間に総とっかえになる前提で見てください。

## 致命的問題

### 1. スキーマがKVSで、関係も型も制約も存在しない
`supabase_schema.sql:5-10`:
```sql
create table if not exists ps_data (
  id          bigserial primary key,
  key         text not null unique,
  value       jsonb not null,
  ...
);
```
- **正規化ゼロ**。Company / Contract / Participant / MeetingLog / HealthScore / SuccessPlan などすべての概念が一つのJSONBに同居。
- 外部キー、CHECK制約、NOT NULL（valueの中身に対して）、ユニーク制約なし。**整合性はアプリ任せ**。
- インデックスは `key` のみ。`value->>'companyId'` で絞り込みたい瞬間にフルスキャン → JSONB GINインデックス必須。
- RLSポリシーが `using (true) with check (true)` で**全公開**。anon keyを知っている人=全データ書き換え可能。これは本番では事故。
- `lib/mock/*.ts` で精緻に切ってある型（`Company`, `Contract`, `Stakeholder`, `AccountJourney`, `SuccessPlan`, `RenewalMilestone` …）が、永続化層では**まったく反映されていない**。フロント型↔DB物理モデルの乖離が深刻。

### 2. メトリクス定義が"画面に書いてあるだけ"で、計算式が存在しない
- `lib/mock/data.ts:146-157` `health` は `green:27, yellow:8, red:7` とベタ書き。`continuousSummary` (data.ts:259-292) の `renewalRate / nrr / attendance / nps` も全部固定値。
- `companyHealthColor` (`health.ts:4-12`) は「contractsの中にredがあれば red」というmin集約のみ。**スコア閾値・重み付け・lookbackウィンドウの定義が存在しない**。
- `deriveHealthScore` (`contracts.ts:70-81`) は **renewalStatusの色から逆算**してscoreを付与する偽の派生（green→90, yellow→70, red→40）。本来 score → color のはずが逆。**因果が逆転**。
- `HealthScore.factors` (`contracts.ts:14-24`) に `attendance / overdueOnboardingTasks / weeksSinceLastTouch / negativeSignalCount` を持つフィールドはあるが、生成側 (`contracts.ts:75`) では `factors: {}` 固定。**設計だけあって実装ゼロ**。
- 解約率・NRR・更新率のSQL/関数定義がどこにもなく、メトリクス辞書（metric dictionary）が存在しない。同じ「更新率」が画面ごとに違う値になる未来が確定している。

### 3. 時系列データを保存できる構造になっていない
- スナップショット（`snapshot`, `health`, `continuousSummary`）は**今日の値だけ**。「先月のヘルス分布」「3ヶ月前のNRR」は再現不可能。
- `mrrTrend` (`data.ts:431-444`) だけは月次の値があるが、**手書きの12点**で、ファクトテーブルから集計したものではない。
- `AccountJourney.history` (`cycles.ts:60`) や `RenewalMilestone` (`cycles.ts:145-152`) のようにイベントログ的な概念は型上はあるが、**永続化される器がない**（KVSなので時系列クエリ不能）。
- 監査列も `updated_at` のみで `created_at` すらない (`supabase_schema.sql:9`)。誰が変更したかも残らない (RLSなし=ユーザー識別なし)。**SCD Type 2 的な履歴管理は皆無**。

### 4. BI / DWH 連携が事実上不可能
- Looker / Metabase / BigQuery / dbt のいずれを繋いでも、`ps_data.value::jsonb` を毎回 `->>` で叩き出すしかない。**dbtでstaging層を組むコストが膨大**。
- ディメンション（Company, Product, Owner, Period）とファクト（Contract events, Health snapshots, Survey responses, Meeting logs）の分離なし。**スタースキーマに展開する余地がない**。
- 「金額」は `mrr` (number) のみで通貨・税区分・期間（月額/年額）の区別なし (`entities.ts:16`, `contracts.ts:35`)。財務との突合不能。

## 重要な懸念

### 5. データ品質・バリデーション・重複検知の不在
- `Company.id` は `c-aeon` のような手書き文字列キー (`entities.ts:23`)。**法人番号(13桁)等の自然キーがない**ため、企業マスタの突合・名寄せが不可能。
- `Contact.email` (`entities.ts:171`) のフォーマット検証なし。`tel?` も任意。`isPrimary` の一意性制約なし → 1社にprimary連絡先が複数存在し得る。
- `Stakeholder` と `Contact` が**別エンティティとして分離**されているが (`entities.ts:165` vs `cycles.ts:33`)、両者の関係（同一人物か）を結ぶキーがない。**人マスタの二重管理**。
- `MeetingLog` (`entities.ts:198-246`) に `aiGenerated` フラグはあるが、**元データへの参照（メールID、議事録ID）がない**。AI要約の信頼度評価ができない。
- `ChurnRecord.reasonCategory` (`churn.ts:7-13`) は固定6カテゴリだが、複数理由の併記不可（多対多にすべき）。`reasonNote` がフリーテキストで集計不能。

### 6. コホート分析・ファネル分析の素地が弱い
- `RenewalFunnel` (`components/RenewalFunnel.tsx`, `data.ts:162-194`) は**3つのバケット（committed/likely/at_risk）の現在状態のみ**。「T-120でyellowだった顧客のうち、T-30でcommittedに昇格した割合」のような**遷移分析が不可能**。
- `accountJourneys.history` (`cycles.ts:63-90`) が唯一の遷移ログだが、配列で保持されているのでSQL集計が困難。**イベントログテーブル（account_id, stage_from, stage_to, transitioned_at）に分離すべき**。
- 入会コホート（契約開始月別）×経過Nヶ月での生存率の算出が、`Contract.startDate` はあれど終了イベントとの結合キーが弱く（`previousContractId`はあるが churn テーブルとのJOINが煩雑）、**コホートテーブルのビューが組めない**。

### 7. 機械学習活用の素地がほぼない
解約予測モデルを組むのに必要な要素が以下のように欠落しています:
- **特徴量となる時系列ログ**: 出席イベント、ログイン、メール開封、面談頻度…の生ログがない。`MeetingLog` はあるが粒度が粗く構造化が浅い。
- **正解ラベル**: `ChurnRecord` (`churn.ts:38-57`) はわずか2件で、しかも `contractId` 文字列のみ。**Contractテーブルとの参照整合性が型レベルで担保されていない**。
- **学習用スナップショット**: 「3ヶ月前のhealthScore + その後churn有無」のペアを再構築するためのpoint-in-timeスナップショットが取れない（前述の時系列保持なし問題）。
- **特徴量ストア候補**: `attendance / nps / overdueOnboardingTasks / weeksSinceLastTouch` などはschema上に名前だけはある (`contracts.ts:14-24`) が値が入らない。

### 8. レポート画面が"飾り"
`app/reports/page.tsx:24-92` の `templates` と `history` は完全な静的配列。「経営向けKPIサマリー」「MRR推移詳細」と銘打ちながら**生成ロジックも、出力フォーマット定義も、データソースSQLもない**。`lastExportedAt` も手書き。実装するときに一からスキーマ設計が必要になります。

### 9. メトリクス値の内部矛盾
- `snapshot.activeContracts = 56` (`data.ts:136`) に対し、`continuousSummary` の合計は `14+18+12 = 44`。**14件分（単発含むとしても）の差分の説明がない**。
- `snapshot.atRiskCount = 7` だが `alerts` 配列は7件で red:3 + yellow:4。一方 `health.red = 7` (`data.ts:149`)。**「at risk = red のみ」「at risk = red + yellow」の定義が画面ごとに揺れている疑い**。
- `periodPerformance.thisQuarter` と `thisFY` の値が完全一致 (`data.ts:222-239`)。コピペバグの可能性大。

## 評価できる点

- **ドメイン分割の方向性は良い**: `Account層` (Stakeholder, AccountJourney) と `Cycle層` (SuccessPlan, RenewalMilestone) を意識的に分けている (`cycles.ts:1-10`)。CSの教科書的なモデリングを踏襲しており、概念整理としては筋が良い。
- **メトリクス候補の語彙が揃っている**: NRR、更新率、出席率、NPS、修了率、リピート率、attendance、negativeSignalCount など、CSアナリストが見たい指標のラベルは網羅されている (`data.ts:259-322`, `contracts.ts:14-24`)。これらを**実装に落とせば**良いダッシュボードになる素地はある。
- **更新マイルストーン (T-120/90/60/30) の標準化**: `renewalMilestoneSpec` (`cycles.ts:138-143`) は仕組みとして秀逸。これをイベントとして時系列保存すればファネル分析の核になる。
- `cycleSyncMode: "global" | "per_account"` (`data.ts:10-11`) のような**業務固有の周期性をモデルで表現**している点は丁寧。

## 改善提案

### 短期（次のスプリント）
1. **メトリクス辞書を1ファイルで定義**: `lib/metrics/definitions.ts` を作り、`healthScore(companyId, asOf)`, `renewalRate(period)`, `nrr(period)`, `attendance(contractId)` を**式で実装**。画面側は必ずこの関数経由で値を取得する。マジックナンバーの`continuousSummary`は廃止。
2. **`deriveHealthScore` の因果逆転を是正** (`contracts.ts:70-81`): factors（attendance, overdueTasks, weeksSinceLastTouch, negativeSignals）から weighted score を算出し、閾値で color を決定する。色 → score の逆算を撤廃。
3. **画面間のメトリクス不整合を解消**: `snapshot.activeContracts` と `continuousSummary` 合計、`atRiskCount` と `health.red` の整合をテストで担保。
4. **Supabase RLSの即時是正**: 認証ベースのpolicyに差し替え。少なくとも `anon` の `update/delete` は禁止。

### 中期（DBリプレース）
5. **正規化スキーマへの移行**: 最低限以下のテーブルに分割。
   - `companies`, `contracts`, `participants`, `stakeholders`, `meeting_logs`, `onboarding_tasks`, `success_plans`, `success_plan_goals`, `renewal_milestones`, `churn_records`
   - すべて `created_at / updated_at / created_by / updated_by` 監査列付き。
   - 外部キーで参照整合性を担保（例: `churn_records.contract_id REFERENCES contracts(id)`）。
6. **イベントログテーブルの新設**:
   - `health_score_snapshots(contract_id, asOf, score, color, factors_json)` を**日次バッチで生成**。これだけで時系列分析・コホート・ML学習データが揃う。
   - `account_journey_events(company_id, product, stage_from, stage_to, transitioned_at)`
   - `attendance_events(participant_id, session_id, attended, recorded_at)`
7. **ディメンション/ファクト分離**:
   - dim: companies, products, owners, dates
   - fact: fact_contract_lifecycle (status遷移), fact_revenue (月次按分), fact_engagement (面談・出席)
8. **企業の自然キー導入**: `companies.corporate_number` (法人番号13桁) を unique で持たせ、外部データ（freee、財務、IR）との突合を可能にする。

### 長期（分析・ML基盤）
9. **dbt + DWH（BigQuery / Snowflake）**: Supabase → CDC → DWH。stagingレイヤでJSONBを展開、martsで `cs_health_daily`, `renewal_funnel_weekly`, `cohort_retention` を提供。
10. **Metric Layer (Cube.js / dbt-semantic-layer)**: 「更新率」の定義を一元化し、画面・Slack通知・経営レポートでの値ズレを撲滅。
11. **解約予測モデルのMVP**: `health_score_snapshots` が3ヶ月分溜まった時点で、特徴量（直近30日の出席率、面談頻度、overdueタスク数、NPS変化）→ 90日以内churn の二値分類をXGBoostで。AUC 0.7 出れば十分実用。
12. **データ品質モニタリング**: Great Expectations / dbt tests で「primary contact が必ず1社1人」「churnedのcontractは必ずend_date < today」等のルールを継続検証。

---

**結論**: 現状は「ダッシュボードのモック」としては成立していますが、**データ基盤としてはゼロからの再設計が必要**です。特に Supabase の KVS スキーマと、メトリクス計算ロジックの不在の2点は、本番運用に入る前に必ず解消すべき致命傷です。

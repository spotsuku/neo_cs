# 顧客視点レビュー（CSポータルで「ラベリングされる側」から見て）

レビュアー視点: 当社（顧客企業）の人事部・経営企画として、NEOのCSメンバーが
このポータルを使って自社にどう接してくるか、を批判的に確認した。
モック実装段階であることは承知の上で、**思想として顧客への配慮が
仕様に組み込まれているか**を見ている。

---

## 総評

率直に言えば、**「顧客は管理対象であって、対話相手ではない」** という思想が
全体に強く滲み出ている。Health色・離脱リスクラベル・ChurnReason・
AI抽出シグナルのいずれも、顧客本人に開示・共有・反論する手段が一切なく、
**CS側だけが知る "陰口メモ" の体系**になっている。

特に深刻なのは以下の3点：

1. **当社の担当者個人（佐藤課長）が "at_risk / 離脱リスク" として顔写真付きで
   分類され、「稼働逼迫で参加頻度低下」と人事評価まがいの所見が記録されている**
   （`lib/mock/cycles.ts:36`）。本人も上長も同意していない。
2. **当社が雑談で漏らした「更新見送り検討中」という一言が、
   永続メモとして固定化されている**（`lib/mock/entities.ts:55`）。
   発言の文脈・撤回・更新が反映される仕組みが見えない。
3. **メール本文が全文保存され、AIで "negative_signal" / "renewal_signal" 等の
   タグを自動付与される**（`lib/mock/email.ts:39, 43-48`）。
   当社にはAI解析されている旨の通知も同意取得もない。

「健全度Green/Yellow/Red」のラベリングが運用上必要なことは理解できる。
しかし**判定根拠が極端に薄く（後述）、当社からは透明性ゼロ、
にもかかわらず社内では "更新可否の重要シグナル" として扱われている**——
この非対称性は、信頼関係を毀損する地雷を内包している。

---

## 致命的問題

### 1. 健全度スコアの根拠が事実上「担当者の主観1色」

`lib/mock/contracts.ts:64-81` を読むと、
HealthScore は `renewalStatus`（green/yellow/red）から決定的に派生されており、
スコア値も `green=90, yellow=70, red=40` の固定マッピング。

```ts
const SCORE_BY_COLOR = { green: 90, yellow: 70, red: 40 };
```

`HealthScore.factors` に `attendance / overdueOnboardingTasks /
weeksSinceLastTouch / negativeSignalCount` というフィールドはあるが、
mock データでは `factors: {}` で**全件空**（contracts.ts:78）。
つまり「色を入れる→スコアが自動で出る」だけで、
**事実根拠は何ひとつ蓄積されていない**。

`lib/mock/health.ts:4-12` の `companyHealthColor` も、
複数契約のうち最悪色を採用するだけで、
"なぜ red なのか" を顧客に説明できる構造になっていない。

→ 顧客から「なぜウチが Yellow なんですか？」と問われても、
   担当者の感覚以外に答えられない。これは契約交渉時の地雷。

### 2. 顧客個人を分類するタグが本人非開示で運用される

`lib/mock/cycles.ts:11-39`:

```ts
type StakeholderType = "decision_maker" | "champion" | "user" | "at_risk";
// ...
{ name: "佐藤 花子", role: "経営企画課長", type: "at_risk",
  note: "稼働逼迫で参加頻度低下" }
```

「離脱リスク」「チャンピオン」「意思決定者」というラベリングを
**本人の名前付きで永続化**している。
GDPR/個人情報保護法の観点でも、
「人事評価類似情報を本人に開示せず保持する」点はグレー。
少なくとも当社の法務・人事から見れば、
**ベンダーが当社社員を勝手に格付けしているという認識**になる。

### 3. アンケートが多すぎ、しかも顧客にメリットが返ってこない

`lib/mock/surveys.ts:297-352` を集計すると、
ACADEMIA 1サイクル（1年）あたりの当社負担：

- 参加者向け: Kickoff後 / 第5回後 / 中間 / 第15回後 / 最終 = **年5回 × 3名 = 15回答**
- 担当者向け定期: 3月・7月・11月 = **年3回**

合計 **年18回のアンケート要請**を当社1社で受ける。
評議会・AIKEN・コミュマネと併用契約していれば、
さらに別枠で発生する（イオン九州は3研修契約 → 試算で年30回超）。

質問内容も `lib/mock/surveys.ts:147-201` を見る限り、
「NPS / CSAT / 講師の質 / 教材の質 / 良かった点 / 改善点」と毎回同じ。
**回を重ねるごとに回答疲労が確実に発生する設計**。
それでいて、回答結果がCS社内で `surveyInsights`（surveys.ts:99-108）に
集約されるだけで、**顧客側にサマリーや改善アクションがフィードバックされる
仕組みがない**。

→ 「集めるだけ集めて、結果は密室」モデル。
   当社としては「またアンケートか、答えても何も変わらないし」になる。

### 4. ChurnRecord（解約理由）が顧客非開示で永続化

`lib/mock/churn.ts:38-57`:

```ts
{ contractId: "k-jrq-academia-1", reasonCategory: "low_engagement",
  reasonNote: "受講者の出席率が低迷、社内成果報告が薄く更新可決が得られなかった",
  nextActionDate: "2026-06-15",
  nextActionNote: "新任部長との関係構築。新コース構成で再アプローチ" }
```

解約した後も、解約理由のCS側解釈と「再アプローチ計画」が記録され続ける。
当社が解約した事実は当社のものだが、
「活用度低迷」「効果実感乏しい」という**カテゴリ分類は当社の合意なし**。
さらに `nextActionNote` で「新任部長との関係構築」と書かれているのは、
顧客側から見れば**「裏ルート開拓計画」**であり、心象は良くない。

## 重要な懸念

### 5. 引き継ぎ品質を保証する仕組みが見えない（「何度も同じ説明」リスク）

`ContractStatus` に `handoff` ステータスはある（`contracts.ts:9`）が、
「前任CSが持っていた暗黙知」を新任に確実に移すデータ構造が薄い。

- `MeetingLog`（entities.ts:183-196）: 議事録は残るが、
  **「顧客の地雷ワード」「触れてはいけない過去経緯」の専用フィールドなし**
- `Stakeholder.note`（cycles.ts:23）: 自由記述1行のみ
- `successPlans`（cycles.ts:110-131）: 目標数値は引き継げるが、
  **そこに至るまでの "なぜこの目標になったか" の合意プロセス**が残らない

→ 担当者が変わると、当社は「あ、この人また最初から聞いてくる…」になる確率が高い。
   特に評議会のように人間関係が重要な研修ではダメージ大。

### 6. オンボが完全にCS都合のスケジュール

`lib/mock/onboarding.ts:32-40` ACADEMIA契約系:

```ts
{ key: "verbal_record",  dueOffsetDays: -30 },
{ key: "nda",            dueOffsetDays: -25 },
{ key: "contract_send",  dueOffsetDays: -20 },
{ key: "contract_return",dueOffsetDays: -10 },
{ key: "invoice",        dueOffsetDays: -5 },
```

開始30日前に内諾、25日前にNDA、10日前に契約書回収——
**当社の決裁プロセス（稟議に2週間〜1ヶ月かかる）を一切考慮していない硬直スケジュール**。
`dueOffsetDays` が研修マスタ固定で、**契約ごとに顧客都合で延ばす機構が見えない**。

`participant:participant_list` も「-21日」「-7日」固定（onboarding.ts:68, 153, 194）だが、
当社側で派遣者を選ぶには社内調整が必要。
**期日超過 = 顧客のせい、として赤色表示される構造**（contractOnboardingItems の status="overdue"）は、
顧客視点で見ると「お前が遅い」と糾弾されている気分になる。

### 7. 顧客の声が改善に反映される回路がない

検索した限り、顧客から発信された要望・不満を**プロダクト改善に紐付ける
データ構造**（FeatureRequest, VoC, etc.）が一切存在しない。

`SurveyInsight` の category に `complaint / suggestion`
（surveys.ts:97）はあるが、これは社内ダッシュボード用であって、
**「この suggestion を製品/運用に反映した」というクローズループ**がない。

WeeklyReview の `more`（weekly.ts:32, 198 など）も
CS社内の振り返り用であって、顧客には共有されない。

→ 顧客の発言は「記録・分類・分析」されるが、「応答・反映・報告」されない。

### 8. プライバシー: メール全文 + AI解析の同意プロセス不在

`lib/mock/email.ts:32-41`:

```ts
type EmailMessage = {
  body: string;  // 全文
  // ...
};
```

`AiExtraction.type`（email.ts:43-48）に `negative_signal`・`renewal_signal` あり。
**当社の担当者が送ったメールが、AIで「ネガティブシグナル」「更新シグナル」と
タグ付けされ、社内共有される**。
通知も同意もポリシー表示も見当たらない。

`mockExtractFromEmail` 等の関数コメントには「Claude API 呼び出しに差し替え」
（email.ts:5-6）とあり、**本番では当社のメールが第三者LLMに送信される計画**。
これは契約書のデータ取扱条項に明記しないと顧客説明が破綻する。

## 評価できる点

公平性のために挙げる：

- **AccountJourney（cycles.ts:55-90）でサイクル横断の文脈を保持**しようとしている。
  「担当者が変わっても、当社との関係史が消えない」設計思想は評価できる。
- **Stakeholder の `activeFrom/activeTo`（cycles.ts:22-23）で、
  当社の人事異動を時系列で追える**ようになっている。
  「離任した人の発言を、いつまでも引きずらない」運用が可能。
- **WeeklyReview の carry-over（weekly.ts:11-13）で、
  CS側のNextが何週も持ち越されたら検知できる**仕組みがある。
  これは「お願いごとを忘れられない」担保として顧客側にもメリット。
- **`MeetingLog.product = "cross"`（entities.ts:188）で、
  複数研修にまたがる話題を分離して扱える**。
  当社のように3研修契約していると、これは助かる。
- **ChurnRecord に `nextActionDate` がある**（churn.ts:14-15）。
  少なくとも「解約後すぐ再営業」ではなく、間を置く設計意図は読み取れる。

## 改善提案

### 優先度: 致命

1. **健全度スコアに事実ベースの根拠フィールドを必須化**
   `HealthScore.factors` を必須にし、
   出席率・オンボ遅延数・最終接点日数などの**自動計算値**を必ず格納。
   担当者の主観色だけでは red にできないようにする
   （contracts.ts:14-24, deriveHealthScore を改修）。
2. **顧客への "Health 開示モード" を用意**
   四半期に1回、顧客に対して「現在の健全度色 + 根拠 + 改善提案」を
   レポートとして共有できる出力機能。
   裏帳簿運用をやめ、対話の素材にする。
3. **Stakeholder.type = "at_risk" のような個人格付けは廃止 or 匿名集計化**
   個人名と「離脱リスク」を直接結びつける記録は法務リスク。
   `note` に文脈を書くまでに留め、type は外す（cycles.ts:11）。
4. **アンケート設計の見直し: 頻度上限と回答負担スコアを導入**
   1顧客あたり「直近30日で送ったアンケート数」をシステムが認識し、
   閾値超過で送信ブロックする仕組み。
   `surveys.ts:55` の SurveySchedule に `cooldownDays` を追加。

### 優先度: 高

5. **ChurnRecord.reasonCategory は顧客と合意した上で記録**
   解約理由の最終確定を「CS側解釈」ではなく「顧客との合意ログ」にする。
   `churn.ts:4` に `agreedWithCustomer: boolean` を追加し、
   未合意のまま分類されているレコードを可視化。
6. **オンボテンプレに「顧客側調整余地」フラグ**
   `OnboardingTemplateItem`（onboarding.ts:11-17）に
   `customerNegotiable: boolean` と `defaultBufferDays: number` を追加。
   開始30日前NDA固定をやめ、顧客の決裁速度に応じて自動延伸。
7. **VoC（Voice of Customer）クローズループの追加**
   `SurveyInsight` の `suggestion / complaint` から、
   `ProductImprovement` エンティティへの紐付けを実装。
   さらに「顧客への回答テンプレ」を生成し、
   **「ご意見を○○に反映しました」を顧客に返す導線**を作る。
8. **メールAI解析の同意 & 透明性**
   `EmailThread` に「AI解析対象 ON/OFF」を企業単位で設定できるフラグを追加。
   AIExtraction を行ったメールには、顧客に対しても
   「このやりとりは要約・分析対象です」とフッター明示できる仕組み。

### 優先度: 中

9. **引き継ぎ専用ドキュメント構造の追加**
   `Handoff` エンティティ（前任CS → 後任CS）を新設。
   - 「触れてはいけない過去経緯」
   - 「顧客の地雷ワード」
   - 「成功した会話パターン」
   を構造化フィールドで記録。
   契約 status="handoff" 時に必須化（contracts.ts:8）。
10. **顧客向けポータル（Read-only ビュー）**
    顧客側の田中部長クラスがログインして見られる
    「進捗ダッシュボード」を将来構想に入れる。
    SuccessPlan の達成率（cycles.ts:103-108）など、
    **共有することで価値が生まれる情報**は積極開示。
11. **Memo フィールドのスナップショット化**
    `Company.memo`（entities.ts:17）の自由記述に
    「いつ・誰が・何文脈で」書いたかのメタ情報を必須化。
    "更新見送り検討中と発言" のような断片が永久保存されないよう、
    有効期限 (`expiresAt`) を持たせる。

## 顧客として、最後にひとこと

このシステムを「真摯に使うCS担当」が当社についたなら、
おそらく良い体験ができる。
しかし**仕様自体が "悪意ある運用を抑止しない"** ので、
担当者ガチャの振れ幅が大きくなる。

「Healthが Red だから、田中部長が次に提示する更新条件はこう揺さぶろう」
「佐藤課長は at_risk タグついてるから、外して話を進めよう」
——こういう運用を、**仕様レベルで防いでほしい**。

健全度・リスク・解約理由は、本来**顧客と一緒に見て、一緒に直す**もの。
密室で記録するための道具にしないでほしい。

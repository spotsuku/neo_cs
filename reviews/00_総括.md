## エグゼクティブ・サマリ

**現状は「精巧なプロトタイプ」であり、本番運用可能なシステムではない。**

15視点のうち **12視点が「致命的問題あり」** と評定。共通して指摘された根本問題は以下4点に集約される。

1. **データ層が事実上存在しない** — 全画面が `lib/mock/*.ts` (約4,500行) のハードコードで動作。Supabase スキーマは `ps_data(key, value jsonb)` のKVS1テーブルのみで、RLSは `allow_all`。新フロント (neo-cs-v2) と既存API (`server.js`/`api/*.js`) は接続されていない。
2. **セキュリティ・コンプライアンスが本番投入不可レベル** — RLS全開放、CORS全許可、`/api/claude` 無認証プロキシ、初回ユーザー自動admin、CSRFなし、監査ログなし、個情法28条違反相当のメール本文越境送信。
3. **CSの中核機能が「画面はあるがロジックがない」** — Healthスコアは色定数の写像、解約予兆エンジン不在、メンバーマスタ不在、エクスパンション/NRR導線ゼロ、Profit Center機能なし。
4. **意思決定に使える数字が出ない** — MRR/ARR/Churn/LTV/At-Risk MRR が固定値またはハードコード。Q1値とFY値が同一の不具合あり。コホート分析・解約予測の素地なし。

## 横断的に複数視点から指摘された共通問題 (優先順)

### P0 — リリース前に必ず解消

1. **RLS `allow_all` ポリシー** (`supabase_schema.sql:25-30`)
   指摘視点: 情シス, 法務, SRE, 将来運用者, データアナリスト
   → 全データを誰でも読み書き可能。anonキーが流出した時点で全社情報漏洩。
2. **`/api/claude` 無認証プロキシ + 任意プロンプト透過** (`api/claude.js`)
   指摘視点: 情シス, 法務, SRE, 他部署連携
   → 誰でもAnthropic APIキーを消費可能、メール本文を米国に同意なく送信。
3. **保存ボタン未配線・ドラフトlocalStorage永続化なし** (`CompanyWeeklyEditor.tsx:259` 他)
   指摘視点: CS入力者, CS責任者, CSマネージャー
   → 入力者が業務に使えない致命傷。リリース不可。
4. **初回ユーザー自動admin化** (`api/auth.js:107-108`)
   指摘視点: 情シス, 法務, 将来運用者
5. **同意・利用目的明示UIなし & 監査ログ皆無**
   指摘視点: 法務, 情シス, 顧客, 財務経理

## 経営判断としての提言

レビュー横断で導かれる結論は以下の3択。

**A. 本格内製を継続するなら** — 最低でも以下を3ヶ月で完了させる必要がある。それができないなら本番投入は危険。
- データ層の本格構築 (Postgres正規化スキーマ + RLSポリシー設計 + イベントログ)
- 認証/認可の作り直し (Supabase Auth + RBAC + 監査ログ)
- mock→repository層への抽象化
- テスト・CI整備
- セキュリティレビュー外部委託
推定工数: シニア2名 × 3ヶ月 + 法務/セキュリティ予算

**B. SaaS移行 (Gainsight, ChurnZero, HubSpot Service Hub等)** — 経営者視点レビューが推奨。
- MRR規模 (推定842万円) に対し、自前CSプラットフォーム維持の経済合理性は乏しい
- 今のプロトタイプは「要件定義書」として活用し、SaaS設定の元にする

**C. ハイブリッド (推奨)** — SaaSコアに、自社固有部分のみ薄く内製。
- 顧客マスタ・契約・Healthは SaaS
- 週次レビュー・社内オンボチェックリスト等の社内ワークフローは neo-cs-v2 を活用
- 既存のドメイン語彙資産を活かしつつ、コア機能の不備を回避

# CSマネージャーレビュー — NEO CSポータル v2

レビュー対象: `/Users/furuken/dev/neo_cs/neo-cs-v2/`
観点: CSチーム中間管理職（5〜10名のメンバーを管掌）として、メンバー稼働の見える化・属人化検知・負荷平準化・1on1運用・品質管理・エスカレーション・教育標準化

---

## 総評

率直に言って、**「現場担当が1社1社の進捗を追う」ためのツールとしては完成度が高いが、「マネージャーが組織として5〜10人を回す」ためのツールとしてはほぼ機能しない**。

- 「企業 × 研修 × 週」軸では充実（`app/weekly/page.tsx`, `WeeklyTable.tsx`）
- 「**メンバー × 担当社数 × 稼働 × 品質**」軸の画面が**1つも存在しない**
- 担当者は単なる文字列（"古野"/"三木"/"松田"の3名ハードコード: `app/weekly/WeeklyTable.tsx:29`, `app/weekly/CompanyWeeklyEditor.tsx:27`, `app/inbox/InboxView.tsx:20`, `app/companies/[id]/WeeklyReviewPanel.tsx:24`）で、**ユーザーマスタも組織マスタも無い**
- マネージャー観点のKPI（メンバー別Stuck数、SLA違反者ランキング、対応件数偏重、未入力率）はどこにも集計されていない
- 1on1機能はそもそも無く、`app/me/page.tsx` も自分用ビューであってマネージャーがメンバーを見るUIではない

**「私が新任マネージャーとして来週月曜の朝にこの画面を開いて、誰のフォローに入るべきか判断できますか？」 → No.**

## 致命的問題

### F-1. メンバーマスタが存在しない（担当者は文字列ハードコード）
- `app/weekly/WeeklyTable.tsx:29` `const ASSIGNEES = ["古野", "松田", "三木"];`
- `app/weekly/CompanyWeeklyEditor.tsx:27` 同上
- `app/inbox/InboxView.tsx:20` `const ASSIGNEES = ["古野", "三木", "松田"];` ※順序すら不一致
- `app/companies/[id]/WeeklyReviewPanel.tsx:24` 同上

→ 退職・異動・チーム再編時に**4箇所を手で書き換える運用**。マネージャーが配下5〜10名を管理する想定なのに、メンバー追加時の運用が破綻している。`User` エンティティが無いため、稼働集計・権限・1on1ログを後付けする土台が無い。

### F-2. メンバー別ダッシュボードが存在しない
- `app/me/page.tsx` は自分用。マネージャーが「松田の今週の状況を見る」UIが**1つも無い**
- `app/dashboard/[product]` は研修軸。担当者軸ビューは無い
- `app/companies/page.tsx:138` の「担当者: すべて」フィルタは存在するが、これは**企業一覧をフィルタするだけ**で、担当者ごとの集計は出ない

→ 「松田が今何社を抱え、何件遅延し、何件Stuckか」を1画面で把握する手段が無い。1on1準備に毎回担当者フィルタで企業一覧を眺めて頭で集計する羽目になる。

### F-3. 業務量の偏り検知が不可能
- `entities.ts` を見ると12社中 古野5社 / 三木4社 / 松田3社（`lib/mock/entities.ts:28-154`）
- `bulk-data.ts` では古野が偏って多い
- しかし**契約数・MRR重み付け・案件難易度（Health Red比率）でメンバー負荷を可視化するUIはゼロ**
- `app/weekly/page.tsx:144-153` の `assigneeCounts` は1企業内のNext担当比率のみ。横断ビューに昇華されていない

→ 古野が1人でAcademia案件をほぼ全部回している（`weekly.ts:126,146,159,173,188` など全て古野author）状況だが、マネージャー画面には「古野が過負荷」アラートが一切出ない。

### F-4. 1on1・週次レビューミーティング運用の機能が皆無
- `weekly/` は「企業×研修×週」のレビュー記録であって、**「上長がメンバーと行う1on1の記録」ではない**
- 1on1ログ、目標管理（OKR/MBO）、評価メモ、キャリア対話のテンプレ、いずれも無い
- マネージャーが「先週の松田との1on1で約束したアクション」を追跡する仕組みが無い

→ 中間管理職の最重要業務である1on1運用がツール外（Notion/Slack等）に流出する前提。CSポータルを謳いながらマネージャー業務の中核を支えていない。

### F-5. 属人化検知が組織として無い
- `weekly.ts` を読むと、イオン九州ACADEMIAは**5週連続で古野が単独author**（`weekly.ts:146,159,173,188`）。代替不能な状態。
- 西日本鉄道評議会は**3週連続で三木がauthorかつアクション未完**（`weekly.ts:230-261`）でstuck。1人で抱え込んでいる兆候。
- にも関わらず「ある企業が単一メンバーに長期依存している」「2人目バックアップが無い」を**検知するロジック・UIが存在しない**

→ メンバーが急病・退職した瞬間に複数顧客が宙に浮く。マネージャーが事前察知する手段が無い。

## 重要な懸念

### W-1. 品質ばらつきの可視化ゼロ
- 週次レビューの「Good / More」自由記述（`weekly.ts:32-33`, `WeeklyTable.tsx:211-234`）は文字数も論点粒度もバラバラ
- イオン×ACADEMIAの古野は4週分とも具体的（`weekly.ts:140,154,168,182`）だが、福岡銀行commuの記述は短く粒度が浅い（`weekly.ts:269-274`）
- 「メンバーごとの記述品質スコア」「Goodが空の率」「Moreがネガティブシグナル含有率」のような品質ダッシュボードが無い
- アンケートNPSの担当別集計（誰の担当顧客が満足度高いか）も無い

### W-2. アラート/エスカレーション設計が貧弱
- Stuck検知 (`weekly.ts:301-306`, `WeeklyTable.tsx:266-270`) は実装されているが、**しきい値2週固定・通知無し・マネージャー宛のサマリ無し**
- SLA超過 (`InboxView.tsx:115-118`) は表示するだけで**担当者別集計・上長への自動エスカレーション・連続違反者アラートが無い**
- 「Red Health 3週継続」「未入力2週連続」「Next Action 期限超過5件以上」などの**運用閾値ルールが定義もUIも無い**

### W-3. 週次入力カバレッジが個人責任に閉じている
- `app/weekly/page.tsx:206-214` の KPI は「入力済企業数 / 未入力企業数」を出すが、**担当者別の未入力率が出ない**
- 「松田の担当7社中、今週未入力3社」のような表示が無いと、マネージャーは入力督促の宛先を作れない
- `bulkMode` (`weekly/page.tsx:244-254`) も自分の未入力を一括埋めるための機能で、上長から「あなた担当の未入力リマインド」を出す機能ではない

### W-4. 出席記録・参加者エンゲージメントが現場止まり
- `participants.ts:136-264` には参加者出席率・属性別集計の計算ロジックが豊富にあり良い
- だが**CS担当者ごとの「自分の担当顧客の出席率平均」「自分の担当の脱落者数」を集計する関数が無い**
- `attendance/AttendanceClient.tsx:118` `recordedBy: "古野"` ハードコード — 誰が記録したか追跡可能だが、それを使ったメンバー稼働分析は無い

### W-5. レポート出力が「外向け」のみで「内部マネジメント向け」が無い
- `app/reports/page.tsx:24-79` の6テンプレートはすべて経営/顧客向け（月次CS、KPI、MRR、研修別実績、At-Risk、更新パイプライン）
- **「メンバーごとの稼働サマリ」「チーム週次レビュー」「1on1準備資料」テンプレが無い**
- 中間管理職が自分のチームを振り返る材料が出力できない

### W-6. 教育・標準化への貢献ゼロ
- 良いGood/Moreの書き方テンプレ、優れたNext Action事例集、新人オンボーディング用チェックリストなどの**ナレッジ共有面が皆無**
- `app/help/` は存在するが中身を見ると一般的なヘルプであり、CS業務標準化とは別物
- 新人が古参（古野）の週次入力を学ぶ動線が無い → 属人化を加速

### W-7. AI抽出の責任所在が曖昧
- `InboxView.tsx:125-129` 抽出の承認/却下が誰でもできる。誰が承認したかの記録が見当たらない
- マネージャーとして「松田が承認した抽出のうち後で却下された率」のような品質指標が取れない

## 評価できる点

- **Stuck検知のロジックが秀逸**: `weekly.ts:301-306` の `weeksStuck` と `WeeklyTable.tsx:266-270` の視覚化は、現場の停滞案件を見つける武器になる。マネージャー集計に昇華すれば即戦力。
- **持ち越しNextの自動キャリーオーバー設計**（`weekly.ts:11,12` の `fromPrevWeek` / `carriedFromWeek`）が思想として正しい。やり残しが消えない。
- **担当者フィルタ**（`app/companies/page.tsx:66`, `app/weekly/page.tsx:184-188`）と**未入力企業ソート**（`weekly/page.tsx:191-196`）は最低限ある。
- 出席記録の `recordedBy` 保持（`participants.ts:111-129`）は監査性◎。担当者別の活動量集計に使える素地がある。
- 週次テーブル `WeeklyTable.tsx` のスティッキーヘッダ・編集UIは現場ストレスが少ない。
- `participants.ts:191-264` `productAttendanceByAttribute` のような横断集計関数があるので、**同じ要領でメンバー横断集計関数を足せば短期で改善できる**素地はある。

## 改善提案

### 最優先（マネージャー機能の0→1）

1. **`User` マスタを切る** — 4箇所のハードコード `["古野","松田","三木"]` を `lib/mock/users.ts` に集約し、role（manager/member）、teamId、capacityWeight などを持たせる。これがないと以降全部詰む。
2. **`/team` ページを新設** — マネージャーログイン時に「配下メンバー一覧」「各人の担当社数 / 今週未入力数 / Stuck数 / SLA超過数 / Open Inbox数」をテーブル表示。1on1直前の3分で全体を把握できる粒度。
3. **メンバー個人ページ** `/team/[memberId]` — 担当企業一覧、過去4週の週次入力履歴、Good/Moreサンプル、Next Action完遂率、出席記録活動量、NPS担当顧客平均。**1on1の議論材料がここで完結する**ように。
4. **属人化アラート** — 「単一メンバー author 比率 > 80% かつ 連続4週以上」の企業×研修ペアをリスト化（`weekly.ts:284-288` の応用）。
5. **負荷スコア** — 担当社数 × 平均Health重み × 平均Stuck数で `loadScore` を算出し、`/team` にヒートマップ表示。

### 高優先（運用が回る）

6. **1on1ログ機能** — `weekly/` と別に `/one-on-one/[memberId]` を新設。週次でテンプレ化（先週の振り返り / 困っている案件 / 来週の集中点 / キャリア対話）。これがあって初めて中間管理職向けと言える。
7. **担当者別の未入力カバレッジKPI** — `weekly/page.tsx:206-214` のKPIに「メンバー別未入力率」を追加。マネージャーは督促の宛先を1クリックで作れる。
8. **アラートルール設定UI** — `/settings/alerts` を作り、Stuck週数閾値、SLA超過件数閾値、Health Red連続週数閾値などを設定 → メール/Slack通知（モック可）。
9. **品質指標** — Good/Moreの文字数中央値、空欄率、ネガキーワード検出率をメンバー別に出す。レビュー会議のネタになる。

### 中優先（標準化・教育）

10. **「お手本」ピン止め機能** — 良い週次入力例をマネージャーがピン止めし、新人が `/weekly` 入力時にサジェストで参照できる。
11. **新人オンボーディングチェックリスト** — 入社からN週でやることをタスク化。`onboarding.ts` を流用しつつメンバー向けに転用。
12. **AI抽出承認の監査ログ** — 誰が approve/reject したかを記録（`email.ts` の `AiExtraction` に `reviewedBy` 追加）し、メンバー別の承認品質を見えるように。
13. **レポート出力に「チーム週次サマリPDF」を追加**（`reports/page.tsx:24-79` のテンプレに）。マネージャーが上長へ提出する資料を1クリックで。

### 低優先（ガバナンス）

14. **権限モデル** — マネージャーのみ閲覧可（評価メモ等）、メンバーは自分の1on1ログのみ閲覧、など。現状は誰でも何でも見える。
15. **「振り分けの提案」AI** — 新規企業を担当アサインする際、現負荷とドメイン経験から候補を提案。

## 一言で

**「現場担当者が1社を深掘るための画面」は十分。「マネージャーがチームを回すための画面」はほぼ未着手。** ハードコード `ASSIGNEES = ["古野","松田","三木"]` がそれを象徴している。Userマスタ整備→`/team` ダッシュボード→1on1ログの3点を入れない限り、CSマネージャーはこのツールを"自分の道具"として使わず、結局スプレッドシートに戻る。

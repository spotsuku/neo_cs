# CSポータル 財務・経理レビュー

レビュー基準日: 2026-05-03 / レビュー対象: `neo-cs-v2/` 配下
レビュー観点: MRR/ARR算定根拠の透明性、解約損失の可視化、売上認識タイミング、契約サイクルと請求の整合、監査証跡、freee連携可能性、個社別LTV

---

## 総評

財務・経理の責任者として率直に申し上げると、現状の本アプリは **「営業/CS現場のダッシュボード」としては綺麗にまとまっているが、財務管理ツールとしての要件をほぼ何一つ満たしていない**。表示されている金額の大半が **手書きの集計値（マジックナンバー）** で、契約データから自動導出されておらず、**仕訳・請求・会計帳簿との突合が不可能**。「MRR ¥8,420,000」という数字を経営会議で報告した瞬間に、「その内訳は？根拠契約のリストを出して」と聞かれて即座に詰む構造になっている。

特に致命的なのは以下3点:

1. **トップダッシュボードのMRR/ARR/GMVが個別契約から自動集計されていない**（`lib/mock/data.ts:133-141, 245-322`）
2. **解約による損失額（lost MRR / lost ARR）がどこにも表示されていない**（`churn.ts` は理由テキストのみ、金額情報なし）
3. **監査証跡（誰がいつどの金額を変更したか）が完全に欠落している**

「v2 / モック」とのディスクレーマーは理解しているが、**データモデルの段階で財務要件を考慮しておかないと、本番化時に全テーブル設計をやり直すことになる**。今のうちに指摘しておく。

---

## 致命的問題

### F-1. MRRがハードコードされており、契約マスタと整合しない
`lib/mock/data.ts:133-141` の `snapshot.mrr = 8_420_000` は、`onboarding.ts:280-284` のアクティブ契約の `mrr` 合計（≒ 1,170,000円。継続型のみ集計）と桁違い。同様に `continuousSummary.academia.mrr = 4_200_000`（`data.ts:262`）も契約合計と整合していない。

- ダッシュボードの数字と、その下の `ContinuousProductCard`（`components/ContinuousProductCard.tsx:23-26` で契約を再集計）の数字が**別ソース**から出ている。経理の世界ではこれは「同じ指標が2系統で違う値を出す」状態であり、即監査NG。
- **MRR は必ず契約マスタから単一導出されなければならない**。中央に `function calcMrr(asOf: Date): { total: number; byCompany: ...; byProduct: ... }` を1つだけ置き、ダッシュボードもプロダクトカードもこれを呼ぶべき。

### F-2. 解約による損失額（Churned MRR / ARR Impact）が一切可視化されない
`lib/mock/churn.ts:4-18` の `ChurnRecord` は、解約理由のテキストと再アプローチ予定だけを持ち、**金額フィールドが存在しない**。`RenewalView.tsx:295-403` の再アプローチタブも、「解約日」「理由」「次回予定日」のみ表示し、**いくら失ったかが画面上どこにも出ない**。

- 経営判断に最も必要な「Churn による Lost MRR / Lost ARR / 累計逸失収益」が**ゼロ秒で見えない**。
- `mrrTrend` (`data.ts:431-444`) も Net MRR の単一ラインのみ。**New MRR / Expansion / Contraction / Churn の4成分分解（いわゆる MRR Movement / Waterfall）が無く、増減要因が説明できない**。NRR 96% (`hyogikai`) と書いてあっても、その内訳を質問されて答えられない構造。
- 改善: `ChurnRecord` に `lostMrr: number; lostArrAnnualized: number` を追加し、`/dashboard` 上部に「今月のChurn損失 ¥XXX,XXX / 累計 ¥X.XX億」をKPIカードとして固定表示する。

### F-3. 売上認識（Revenue Recognition）の概念が完全欠落
日本基準でもIFRS15/ASC606でも、SaaS/研修サービスは **役務提供期間にわたって按分認識** が原則。本アプリは:

- `Contract` (`contracts.ts:26-45`) に `mrr` と `revenue` というフィールドがあるが、**`revenue` の意味が未定義**（契約金額総額か、認識済か、請求済か不明）。
- 単発型 AIKEN の `oneShotSummary.fyGmv = 8_240_000` (`data.ts:314`) は **GMV（流通総額）** を表記しているが、開講中（`activeCourses: 2`）であれば、契約日基準と役務提供日基準で計上時期が変わる。**繰延収益（前受金）残高がどこにもない**。
- `commu` は3ヶ月サイクル（`data.ts:69`）で1サイクル ¥360,000（=¥120,000 × 3）の前受。期初に一括請求した場合、**月次按分で認識すべき繰延残高 ≒ 全アクティブ契約 × 残月数**を保持・表示すべきだが、計算ロジック皆無。
- `periodPerformance.thisQuarter.grossRevenue` と `thisFY.grossRevenue` が **同じ ¥33,410,000**（`data.ts:228, 237`）。Q1 = FY全体になるはずがない（FYは継続中）。**ダミーとはいえ、財務ダッシュボードでこの値が出るのは絶対NG**。経営会議で見せたら一発で信頼を失う。

### F-4. 契約サイクル（cycles.ts）と請求の整合が取れない
`cycles.ts` は SuccessPlan / RenewalMilestone / Stakeholder を扱うが、**請求サイクル（請求書発行日、請求金額、入金予定日、入金実績、与信）が完全に欠落**している。

- `products[].billingMonths`（`data.ts:31, 44, 56, 68`）に「請求周期」と書いてあるが、**実際の請求書発行・入金管理テーブルが無い**。これでは「未入金一覧」「売掛金齢分析（AR aging）」が出せない。
- `renewalMilestoneSpec` は T-120/-90/-60/-30 で更新営業の節目を持つが、**「次の請求書を発行すべき日」**というマイルストーンが無い。CSと経理で別系統管理になり、必ず請求漏れが発生する。
- `generateRenewalMilestones`（`cycles.ts:161-174`）は `TODAY = "2026-04-24"` を**ハードコード**。本番化したら時刻依存テストが地獄になる前に直すべき。

## 重要な懸念

### F-5. 監査証跡（Audit Log）が皆無
- `Contract`、`ChurnRecord`、`SuccessPlan` 等いずれも `createdBy` / `updatedBy` / `updatedAt` / 変更履歴 が無い。
- `RenewalView.tsx:69-76` の `markDone` は React state を書き換えるだけで、**「誰が」「いつ」「なぜ」完了にしたのかの記録が一切残らない**。SOX的観点でも内部監査でも通らない。
- 改善: 全ての金額関連エンティティに `audit: { createdBy, createdAt, updatedBy, updatedAt }` と、別テーブルで `audit_log(entity, entityId, field, oldValue, newValue, actor, at, reason)` を必須化。

### F-6. NRR / Renewal Rate の定義と計算式が不透明
- `continuousSummary.*.nrr`（`data.ts:265, 276, 287`）は単なる定数値。NRR は「期初MRR + Expansion - Contraction - Churn」÷「期初MRR」と定義式を画面に明示すべき。
- `renewalRate: 0.92` も同様に「分子＝更新合意件数」「分母＝期末到来件数」の母集団期間が定義されていない。**取締役会用KPIで定義書が無いのは致命的**。

### F-7. 個社別 LTV / 収益貢献が見えない
- `companies` ページ群はあるが、**「この企業からの累計売上」「平均契約期間」「LTV」「粗利貢献」「割引率込みの実質単価」「次回更新時の見込MRR」が個社詳細画面に出ない**（`ContinuousProductCard.tsx`、`OneShotProductCard.tsx` も同様で社別集計なし）。
- 営業コスト・CAC との突合もできない。「イオン九州にいくら使っていくら稼いだか」が30秒で出ない CS ツールは、財務責任者から見ると価値が半減している。

### F-8. 通貨・端数・税抜税込・割引の扱いが未定義
- `yen()` (`data.ts:449-453`) は表示フォーマッタとしては機能するが、**税抜/税込の区別フラグなし**、消費税率（10%）の扱いなし、複数通貨への拡張不能。
- 値引き・キャンペーン適用後の契約MRRは元価格と分離管理すべき（`Contract.listPriceMrr`, `Contract.discountAmount`, `Contract.netMrr`）。今は `mrr` 一本で履歴が残らない。

### F-9. freee 連携設計が皆無
プロジェクトには freee MCP が利用可能とあるが、コードベースに freee 連携の痕跡がゼロ（grep結果より）。少なくとも以下が必要:

- 契約 → freee 請求書ドラフト自動生成（`Contract.startDate` / `billingMonths` を起点にスケジュール化）
- freee 入金実績 → 本アプリの「入金ステータス」自動同期
- freee 取引先IDと `companies[].id` のマッピングテーブル
- 月次のMRR集計値と freee 売上計上額（按分後）の差異レポート

これらを **MCP経由の同期ジョブとして設計** することで、CS担当が手で会計入力する必要がなくなる。`freee_api_get` / `freee_api_post` で受発注・請求書APIを叩く想定で `lib/integrations/freee/` を切るべき。

## 評価できる点

- `Contract` 型 (`contracts.ts:26-45`) に `cycleNumber` / `previousContractId` が用意されており、**サイクル間の繋がりを辿れる構造**になっている点は LTV 算出の基礎として優秀。これは活かせる。
- 単発型と継続型を `ProductType` で分離（`data.ts:5, 11-23`）し、`MRR を持つもの／GMV のみのもの` を型レベルで区別している点は会計区分の前提として妥当。
- `RenewalMilestone` (`cycles.ts:138-152`) で更新前の T-120/-90/-60/-30 が機械的に生成されるのは、更新失敗による収益逸失リスクの早期警報として有効。**ここに「請求マイルストーン」を相乗りさせれば、経理連携の足場になる**。
- `ChurnRecord` に `nextActionDate` / `nextActionNote` がある点は再獲得（Win-back）KPI の基礎として良い。金額を載せれば即実用化できる。

### 結語
**現状はCS現場の業務支援としては良くできているが、「財務に説明可能なダッシュボード」ではない。** ハードコード値を契約マスタからの導出に切り替え、Churn損失を可視化し、freee連携で会計と整合させる。この3点が揃って初めて、経理がこのアプリの数字を信用できる状態になる。

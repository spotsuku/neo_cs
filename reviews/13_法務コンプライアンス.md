# 13. 法務・コンプライアンスレビュー

レビュアー: 法務・コンプライアンス責任者（外部視点・辛口）
対象: `/Users/furuken/dev/neo_cs/`（API、`neo-cs-v2`フロント、Supabaseスキーマ）
レビュー日: 2026-05-03

---

## 総評

率直に申し上げて、**現状のままで顧客企業の本番個人データを投入すれば、改正個人情報保護法（令和2年改正・令和4年4月施行）違反のリスクが極めて高く、また顧客との秘密保持契約（NDA）違反、越境移転規制違反を同時に構成する可能性があります**。

本システムは「CS（カスタマーサクセス）」を標榜しながら、実態は **顧客企業の従業員（受講者・担当者）の氏名・メールアドレス・所属部署・役職、加えて受信メール本文をそのままAI（Anthropic）に送信し、Supabaseに恒久保管する** 構造になっています。これらは個情法上の「個人データ」に該当し、かつ顧客企業の側から見れば「自社従業員の個人情報を、研修ベンダーが自社の業務効率化目的で外部AIに転送している」という状況です。

それにもかかわらず、

- プライバシーポリシー／利用目的の明示画面が**ゼロ**
- 監査ログ（誰がいつ何にアクセスしたか）の仕組みが**完全に欠如**
- 越境移転（Anthropic米国、Supabaseリージョン未確認）に関する利用者・顧客への説明が**なし**
- 退職者・契約終了顧客のデータ削除フローが**未実装**（`status: "inactive"`型はあるが削除トリガーなし）
- AI自動評価（健全度カラー、AI抽出）に対する**異議申立・訂正請求の窓口・フローなし**
- RLS（行レベルセキュリティ）が`allow_all`で**事実上無効化**

という有り様です。社内ツール・PoC段階という弁明は通用するレベルを超えています。**本番運用に入る前に、最低でも「致命的問題」全項目の是正、および顧客との覚書（個人データ取扱に関する特約・AI利用同意）の締結が必要**です。

## 致命的問題

### 1. RLS（行レベルセキュリティ）が事実上無効＝全データが anon key で全件取得可能
- `supabase_schema.sql:26-30`
  ```sql
  alter table ps_data enable row level security;
  create policy "allow_all" on ps_data
    for all using (true) with check (true);
  ```
  **RLSを有効化したフリ**をしているだけで、ポリシーは全許可。`api/db.js:38-42` の `/rest/v1/ps_data?select=key,value&limit=1000` は anon key で全顧客企業のデータをまとめて返却します。
- `api/db.js:11-14` で **`Access-Control-Allow-Origin: '*'`** が設定されており、ブラウザからの任意オリジンアクセスを許容。anon key が JS バンドルに含まれていれば、第三者が curl 一発で全件抜き出せる構造です。
- 個人データ漏えいが発生した場合、改正個情法 **第26条の漏えい等報告義務（個人情報保護委員会への報告 + 本人通知）** の対象。1,000人超の漏えいであれば確実に報告事案。

### 2. 利用目的の特定・通知・公表が一切存在しない（個情法17条・21条違反）
- 設定画面 `app/settings/page.tsx:13-43` に「研修マスタ」「ユーザー管理」「Gmail連携」「通知設定」はあるが、**プライバシーポリシー／利用目的明示／同意取得の画面が一切ない**。
- 顧客企業の受講者個人情報（`lib/mock/participants.ts:49-` 氏名・メール・部署・役職）を取得・保管しながら、利用目的（CS業務、AI解析、健全度スコアリング、更新提案）を本人にも顧客企業にも通知していない。
- 改正法では「**取得時に利用目的を本人が認識できる状態に置く**」ことが必須（21条1項）。社内ツールでも適用除外にはなりません。

### 3. メール本文を Anthropic（米国）に無同意で送信＝越境移転違反 + NDA違反リスク
- `api/claude.js:54-66` は Anthropic API（`api.anthropic.com`、米国）にメッセージを丸ごと転送。
- `app/inbox/InboxView.tsx:131-136`, `app/inbox/extractions/ExtractionsView.tsx` 配下のフローでは、顧客企業からの受信メール本文（`messages[].body`）と担当者氏名・メアドが AI に渡る前提。
- 改正個情法 **第28条（外国にある第三者への提供）** により、本人の同意取得 or 基準適合体制の整備が必要。同意画面なし、Anthropic との委託契約（DPA）の有無も不明。
- 顧客企業との **NDA / 業務委託契約には通常「秘密情報を第三者に開示しない」「再委託には事前承諾」** が含まれる。Anthropic への転送は再委託に該当し、**個別同意なき転送は契約違反**。重大な顧客対しては損害賠償の対象。

### 4. 監査証跡が存在しない（誰がどの顧客データを見たか追跡不能）
- `api/db.js`, `api/auth.js`, スキーマのいずれにも **アクセスログ・操作ログ・変更履歴テーブルが存在しない**。
- `api/auth.js:96-112` で `last_login` のみ記録するが、これは「最後にログインした時刻」であって監査証跡ではない。
- 個情法 **安全管理措置（ガイドライン「組織的安全管理措置」）** で要求される「アクセスの記録」「不正アクセス検知」が未整備。漏えい時に影響範囲特定が不可能 → 報告書作成不能。

### 5. 退職者・契約終了顧客のデータ削除フローなし（個情法22条 = 不要となった個人データの遅滞ない消去）
- `lib/mock/participants.ts:17` に `status: "active" | "inactive" | "dropped"` 型はあるが、**論理削除フラグだけで物理削除・自動削除のジョブが存在しない**。
- 契約終了（`contracts.ts`）後の受講者データ・メール履歴・AI抽出結果の保存期限ポリシーなし。
- 顧客担当者が退職した場合、その個人情報は「**利用する必要がなくなった**」状態（22条）に該当し、遅滞ない消去義務。手動削除画面も無い（`api/db.js:49-58` は key 単位 DELETE のみで、エンドユーザーが触れない）。

### 6. AI自動評価への異議申立権・訂正請求の仕組みなし（個情法34・35条 + 倫理的問題）
- `lib/mock/health.ts` の `companyHealthColor` は `red/yellow/green` を機械的に算定し、`CompanyDetail.tsx` 等で表示。AI抽出（`InboxView.tsx:35-48` の `negative_signal` `renewal_signal` 等）も同様。
- これは顧客企業に対する「自動評価」であり、**評価結果が解約・値下げ交渉・対応優先度に影響する以上、評価対象（顧客企業）には説明と訂正の機会を設けるべき**（経産省・総務省「AI事業者ガイドライン」第3部 透明性・アカウンタビリティ）。
- `negative_signal` のように「ネガティブ」とラベル付けされた個人発言が、本人の知らないところで AI により分類・記録されるのは、本人の権利利益侵害リスク高。

## 重要な懸念

### 7. 最初のログインユーザーが自動で admin 化（権限管理の脆弱性）
- `api/auth.js:106-110`
  ```js
  const role = allUsers.length === 0 ? 'admin' : 'member';
  ```
  本番デプロイ直後に第三者が先にログインすれば乗っ取れる。Google Workspace ドメイン制限（`hd` クレーム検証）も `googleVerify`（`api/auth.js:82-94`）に存在しない → **任意の Google アカウントが member として登録される**。

### 8. `Access-Control-Allow-Origin: *` を全 API で固定
- `api/auth.js:14`, `api/db.js:11`, `api/claude.js:4` すべて `*`。
- これにより、悪意あるサイトから利用者のブラウザ経由で API を叩ける（CSRF的悪用）。Anthropic API キー消費攻撃（`/api/claude` 無認証）も可能 → **API キーコスト爆発 + サービス停止リスク**。

### 9. `/api/claude` に認証・レート制限・入力サニタイズが一切なし
- `api/claude.js:3-39`：誰でも POST 可能、`messages` に何でも詰められる、`max_tokens: body.max_tokens || 1000` で上限指定なし。
- 顧客の機密情報がプロンプトに混入しても検知不能、プロンプトインジェクションで AI が虚偽の「健全度判定」「ネガティブ抽出」を出力する余地。

### 10. Gmail連携の権限スコープ・保存方針が不明
- `app/settings/gmail/` ディレクトリは存在するがコードを確認すると **OAuth スコープ・取得対象の明示や利用目的同意UIがない**。Gmail の全メール本文を取得する設計だとすれば、Google API Services User Data Policy（特に "Limited Use" 要件）に違反する可能性が高い。
- 利用者ではなく **顧客企業の従業員から受信したメール** を AI 解析することについて、送信元の権利者への明示がない。

### 11. Supabase / Anthropic のリージョン・DPA が未文書化
- `api/db.js:17-21` `SUPABASE_URL` のリージョン（東京 ap-northeast-1 か、シンガポールか、米国か）はコード上不明。
- 顧客契約に「データは国内保管」と謳っているなら **契約違反リスク**。Anthropic は米国法人で、APIエンドポイントは米国経由。28条同意 + 提供先国情報（米国の個人情報保護制度）の本人提供義務あり。

### 12. ハードコードされた個人実名 / 個人特定情報
- `app/inbox/InboxView.tsx:18` `const CURRENT_USER = "古野";`
- `lib/mock/participants.ts:49-` に実在しそうな企業名（イオン九州、TOTO、福岡銀行、西日本シティ銀行）と個人氏名・実ドメインメアドが大量。**モックでも実在企業名 + 実ドメイン（@toto.co.jp 等）の組み合わせは名誉毀損・虚偽情報拡散のリスク**。リポジトリ公開時に即削除対象。

### 13. データ主体（顧客従業員）への開示請求対応窓口がない
- 個情法 **33条開示請求、34条訂正、35条利用停止** に対応する画面・フローなし。受講者から「自分の発言ログを見せろ／削除しろ」と請求された場合、対応できない。

### 14. パスワード／APIキーの取扱いに監査がない
- `ANTHROPIC_API_KEY`, `SUPABASE_ANON_KEY` は環境変数だが、**サービスロールキーが必要な操作（RLS bypass）を anon key で実行している**点で、そもそも RLS 設計が成立していない。

### 15. アンケート（surveys）の自由記述に含まれる個人情報の取扱方針なし
- `app/surveys/` 配下で受講者の自由記述が AI 解析対象になる場合、機微な情報（健康、思想、職場の悩み）が混入する可能性。要配慮個人情報（個情法2条3項）が混入した瞬間、取得時の本人同意が必須化（17条2項）。同意フローなし。

## 評価できる点

- `supabase_schema.sql:26` で **RLS 有効化の意図** はあった（ポリシーが穴だらけだが）。最初から `disable` でないのは前向き。
- `api/auth.js:60-65, 71-77` で **管理者権限チェック（`requester.role !== 'admin'`）** を一応実装している。
- `lib/mock/participants.ts:17` で `status: "inactive" | "dropped"` の **ライフサイクル概念は存在**（ただし削除アクションが未実装）。
- Google OAuth による認証採用（`api/auth.js:82-94`）は、自前パスワード保管より遥かにマシ（ドメイン制限さえ加えれば及第点）。
- `app/inbox/InboxView.tsx:418-432` で **AI 抽出結果に対する「承認／却下」UI** が存在 → これを起点に「人間によるレビュー必須」原則を制度化する素地はある。

## 改善提案（優先度順）

### P0（本番投入前に必須・1〜2週間）
1. **RLS ポリシーの本実装**: `policy "allow_all"` を即座に廃止し、`auth.uid()` ベースで `key` プレフィックスごとに read/write を制御。anon key でのフロント直叩きを廃止し、`api/db.js` を service_role key + サーバ側認可に切替。
2. **CORS の絞り込み**: `Access-Control-Allow-Origin` を本番ドメインに固定。`/api/claude`, `/api/db` に **JWT 検証ミドルウェア**（`api/auth.js` の verify を共通化）を必須化。
3. **Google Workspace ドメイン制限**: `api/auth.js:82-94` の `googleVerify` で `hd` クレームを検証し、自社ドメイン以外は拒否。最初のユーザー自動 admin 化（`api/auth.js:107`）は廃止し、初期管理者は環境変数 or マイグレーションで明示指定。
4. **プライバシーポリシー画面 + 利用目的明示 + 同意ログテーブル**: `app/settings/privacy/`（新規）でポリシー掲示、`neo_consent_log` テーブルで「誰がいつ何に同意したか」を記録。
5. **Anthropic / Supabase の DPA 締結とリージョン文書化**: 顧客向けに「AI処理は Anthropic 米国を経由する」「データは Supabase Tokyo に保管」等を明記し、顧客との委託契約に **再委託条項** として追加。28条同意取得画面を Inbox 画面の前に挟む。
6. **受信メール本文の AI 送信ポリシー**: `api/claude.js` 入口で「同意済み顧客の thread か」をチェック。同意なし顧客のメールは AI に流さない設計に。最低でも、顧客名・人名・メアドの **マスキング処理** をプロンプト前に挿入。

### P1（1ヶ月以内）
7. **監査ログテーブル `neo_audit_log`**: `actor_email`, `action`, `target_type`, `target_id`, `payload_diff`, `ip`, `ua`, `created_at` を持ち、`api/db.js` の全操作と `api/claude.js` の AI 呼び出しを記録。最低 1年保管。
8. **データ削除ジョブ**: 契約終了 `contracts.endDate` から N ヶ月（顧客契約に応じて 3 / 12 / 24 ヶ月）経過で関連 `participants` `email_threads` `extractions` を物理削除する Supabase Edge Function を cron 実行。`status: "dropped"` の participant も同様。
9. **データ主体権利対応窓口**: `app/me/data-requests/`（新規）で開示・訂正・削除・利用停止請求を受付、管理者ワークフローへ。
10. **AI評価の透明化**: `companyHealthColor`（`lib/mock/health.ts`）と AI抽出（`InboxView.tsx`）の **算定根拠を顧客企業に開示**できる画面を用意。顧客から「異議あり」を受けた場合に再評価する SLA を定める。
11. **モックデータから実在企業名・実ドメインを除去**: `lib/mock/participants.ts:49-` を `acme-1` `example.test` 等の架空ドメインへ置換。

### P2（3ヶ月以内）
12. **要配慮個人情報の検知**: アンケート自由記述・メール本文に対し、健康・思想等のキーワード検知を行い、検知時は AI 送信を停止 or 追加同意を要求。
13. **Vendor Risk Management**: Anthropic / Supabase / Google の SOC2・ISO27001・国内法対応状況を年次で文書レビュー。
14. **個人情報保護法・GDPR・CCPA に関する社内研修と DPIA（データ保護影響評価）の実施**: 健全度スコアリングは「プロファイリング」に該当するため DPIA 必須。

### 法務責任者からの最終コメント

「社内ツールだから」「モックだから」という言い訳は、本番データを1件でも入れた瞬間に通用しなくなります。とくに **顧客企業の従業員という第三者の個人データ** を取扱う以上、自社従業員データの何倍も慎重な設計が必要です。**P0 を完了するまでは、いかなる本番顧客データも投入してはなりません**。これはエンジニアリング判断ではなく、経営判断として顧客との契約・社の存続に直結します。

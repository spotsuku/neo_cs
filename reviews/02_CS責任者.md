## 総評

UI構造としては「全体俯瞰 → 研修別 → 企業別 → 契約別」という階層が綺麗に整理されており、社内のCSポータルとしての"見せ方"は合格点。しかし**CS現場で本当に解約を防ぎLTVを最大化するための仕組みとしては、現状ほぼ"見える化ダッシュボード"の域を出ていない**。Healthスコアは事実上`renewalStatus`を色変換しているだけで予兆検知は機能しておらず、更新マイルストーンは日付経過のみで`done`扱いという致命的な実装。アップセル/エクスパンションの検知導線はゼロに近く、CS as a Profit Centerの設計思想がコードに現れていない。週次レビュー画面は工夫があるが、Stuck検知以外にチーム運営をドライブする仕掛けが弱い。

机上の空論度は中〜高。"あるべき情報項目を並べた"段階で、CSオペレーションの意思決定を駆動する仕組みは未実装。

## 致命的問題

### 1. Healthスコアが完全に飾り（信頼性ゼロ）

`lib/mock/contracts.ts:64-81`の`deriveHealthScore`は、`renewalStatus`という人手入力色を**そのまま色とスコア(90/70/40の3値)に写像しているだけ**。

```ts
const SCORE_BY_COLOR = { green: 90, yellow: 70, red: 40 };
export function deriveHealthScore(renewalStatus, computedAt) {
  if (!renewalStatus) return undefined;
  return { color: renewalStatus, score: SCORE_BY_COLOR[renewalStatus], factors: {}, computedAt };
}
```

`factors`は空オブジェクト。一方、`components/HealthSection.tsx:135-138`では「Health Score = 出席率 + NPS + 最終接点日数 + 期日超過タスク + メール感情 から合成」と**ユーザに対して虚偽の説明**を表示している。これはCS現場の信頼を一発で破壊するレベル。`lib/mock/health.ts`の`companyHealthColor`も同じ色をmax-severityで集約するだけで、実データ由来のシグナル合成は皆無。

**致命度: 最高。** モックである旨が明記されていてもUI文言と実装の不一致は要修正。

### 2. 解約予兆検知が事実上存在しない

`lib/mock/churn.ts`は**解約後の記録（理由カテゴリ・再アプローチ予定）**しか持たない。「これから解約しそうな契約」を発見するためのシグナルモデル（出席率低下、Champion離脱、Sponsor異動、メール返信途絶、NPS低下、期日超過の累積）が一つも実装されていない。`stakeholders`に`type: "at_risk"`(`lib/mock/cycles.ts:36`)があるのに、これをHealthや更新ファネルに連動させる導線が見つからない。

ダッシュボードの「要対応企業」(`app/page.tsx:148-`)の根拠は、`lib/mock/data.ts:327-`にハードコードされた7件の文字列(`reason`, `suggestedAction`)。**ロジックではない、ただの手書きリスト**。本番データでも同じ仕掛けで「7件並べる」のは無理。

### 3. 更新マイルストーンが「日付経過＝完了」になっている

`lib/mock/cycles.ts:161-174`の`generateRenewalMilestones`:

```ts
const done = new Date(dueDate) < new Date(TODAY);
return { ..., status: done ? "done" : "todo" };
```

T-120/T-90/T-60/T-30は**実施したか否かと無関係に、過ぎたら自動で"done"になる**。`RenewalView.tsx:198-201`の「直近マイルストーン」表示はこれを真に受けて「完了」と表示する。CS現場で最も重要な「更新までのアクションが本当に実施されたか」を捕捉できないのは致命的。

### 4. アップセル/エクスパンション検知が皆無 — Profit Centerの思想なし

- `JourneyStage.expansion`(`lib/mock/cycles.ts:44`)という概念は型として存在するが、**「拡大ステージに到達した企業を一覧化する」「拡大候補をスコアリングする」画面が無い**。
- 「他研修の追加販売余地」「参加者増員余地」「上位プラン提案余地」といったエクスパンション・トリガを算出するロジックなし。
- `successPlans[1].goals`に`{ key: "expand", title: "次期受講者の拡大", achievement: 0.67 }`(`lib/mock/cycles.ts:128`)はあるが、これも単発ハードコード。
- 同一企業で複数研修を契約している（c-aeon, c-toto等）のに、**Cross-Sell機会を提示する画面・KPIが無い**。
- レポート(`app/reports/`)にもNRR/GRR/拡大MRRの指標が出てこない構造。

CSが収益貢献組織であることをコードレベルで示せていない。

### 5. オンボーディング進捗の運用中契約データが嘘になっている

`lib/mock/onboarding.ts:446-456`:

```ts
if (c.status !== "onboarding" && c.status !== "handoff") {
  // 運用中契約: すべてdone
  ...status: "done", completedAt: offsetDate(c.startDate, -1)
}
```

運用中になった契約のオンボ項目は**全件強制的にdone**として記録される。実際には「契約後に発覚する未完了タスク（入金確認漏れ、参加者アカウント発行漏れ）」がCS現場の典型的な事故ポイント。これを"完了済み"として書き換えてしまう設計はTTV計測も振り返りも不可能。

## 重要な懸念

### A. TTV(Time to Value)指標が見つからない

オンボのチェックリスト(`productOnboardingTemplates`)はカテゴリ×項目で整備されているが、**「Kickoffから初回価値到達までの日数」「`adoption`ステージ到達までの日数」を測る指標も画面も無い**。`AccountJourney.history`(`cycles.ts:60`)に滞在期間を計算できる素材はあるのに、活用している箇所が見当たらない。これではオンボ改善のPDCAが回らない。

### B. 週次レビューがチーム運営として弱い

`app/weekly/page.tsx`は研修×週で全社俯瞰でき、Stuck検知（2週以上持ち越し: `lib/mock/weekly.ts:weeksStuck`相当）まである点は良い。しかし:

- **Next Action → 翌週のActionへの自動キャリーオーバーが見えない**。`fromPrevWeek`フラグはあるが、未完了Nextが「自動で翌週Actionに引き継がれる」ワークフローは実装が薄い。
- **担当者ロード/集中度のヒートマップがない**。`assigneeSummary`(`weekly/page.tsx:151`)で名前文字列を出すのみ。マネージャが「松田に偏ってないか」を見るには手作業で数えるしかない。
- **Good/Moreが感情ログ化していて、ナレッジ化・横展開する仕組みがない**。他社事例を検索・参照する導線なし。

### C. attendance/が「単一セッションの出席を打つ画面」止まり

`app/attendance/AttendanceClient.tsx`は1セッション×参加者の出席登録UIとしては動くが、CSマネジメントに必要な以下が無い:

- 参加者ごとの**累積出席率トレンド**（離脱予兆の核心指標）
- セッション横断での**欠席多発参加者の自動検出**
- 出席率がHealthScoreに反映される導線（前述の通りHealthは出席率を見ていない）

これでは「出席を記録するExcelの代わり」にしかならない。Health/Renewalと連動して初めてCS価値が生まれる。

### D. 担当者(`ownerName`)が自由文字列で稼働可視化が困難

`Contract.ownerName`は`string`(`contracts.ts:34`)。`User`エンティティに紐づいておらず、**「松田の現在抱えるアラート総数」「古野が今月追加で持てる契約余力」**を集計する単一情報源がない。`me/`ページや`attendance/AttendanceClient.tsx:118`の`recordedBy: "古野"`もハードコード。

### E. Renewalの提案金額・拡大提案金額がモデル化されていない

`Contract`に`mrr`/`revenue`はあるが、**更新時の「提案金額」「拡大ぶんdelta」を記録する場所が無い**。NRRを算出する基盤がない。`renewalMilestoneSpec`の`T-60: "更新提案"`(`cycles.ts:142`)で扱う提案内容を保存できないのは大きな穴。

### F. 通知/エスカレーションがない

Stuck 2週以上、Health Red、メール無返信21日超、T-30未着手 — これらを検知してSlack/メール通知する機構が見当たらない。**ダッシュボードを開かないと気付けない仕組みは、現場では確実に見落とされる**。

### G. 解約後の再アプローチがChurn 2件のハードコード

`lib/mock/churn.ts:38-57`は**たったの2件**。`/renewal`の再アプローチタブはこのデータに依存。Win-back施策のKPI（再受注率/期間/トリガ）が型レベルで設計されていない。

## 評価できる点

- `Contract`/`AccountJourney`/`Stakeholder`/`SuccessPlan`/`RenewalMilestone`という**CSドメインモデルの分解は概ね正しい**(`lib/mock/cycles.ts`)。Account層とCycle層を分けた点はLTV志向の設計として妥当。
- 週次レビューの「Stuck検知（2週以上持ち越し）」「未入力企業をフィルタ→一括入力モード」(`weekly/page.tsx:244-254`)はCS現場の作業フローを理解した設計。
- 更新ダッシュボードでGreen/Yellow/Red/再アプローチをタブ統合(`RenewalView.tsx`)し、解約後フォロー導線まで一画面に閉じ込めている発想は良い。
- `productOnboardingTemplates`が研修×カテゴリ×項目の3層で、開始日からの相対日数(`dueOffsetDays`)で管理されているのはテンプレ運用として実用的。
- `daysSinceLastTouch`を表示する習慣(`app/page.tsx:184`)はCS的に正しい着眼点（実装は手書きだが）。
- Stakeholderに`type: "at_risk"`、`activeTo`離任記録、`champion`/`decision_maker`の区別がある点はエンタープライズCSの基本を押さえている。

## 改善提案（優先度順）

### P0 — 信頼性に直結する是正

1. **Healthスコアの実シグナル化**: `factors`に`attendance`(直近4週)/`overdueOnboardingTasks`/`weeksSinceLastTouch`/`negativeSignalCount`/`stakeholderChurnEvents`を実データから合成する関数を実装し、`computedAt`との鮮度判定を入れる。`HealthSection`の説明文と一致させる。
2. **更新マイルストーンの完了は「人が完了させた」状態に**: `status`を日付ではなく明示的なアクション(完了登録 or 自動検知された活動ログ)で更新。期日超過は`overdue`として別表示。
3. **運用中契約の「全done上書き」廃止**(`onboarding.ts:449`): 実際の完了状態を保持し、運用フェーズ移行後の未完了タスクを残す。

### P1 — 解約防止/Profit Centerの実装

4. **解約予兆スコアエンジンの新設**: `lib/risk/`配下に
   - Champion離脱 (`Stakeholder.activeTo`埋まり)
   - 出席率の前4週連続低下
   - メール無返信21日超 (`inbox/`連動)
   - Stuck Action 2件以上
   - NPS -15以上低下
   - 期日超過タスク3件以上
   をスコア化し、Healthの`negativeSignalCount`へ反映。`alerts`ハードコードを廃止しエンジン出力に置換。
5. **エクスパンション機会画面**(`/expansion`): 単一研修導入企業に他研修候補を提示、`AccountJourney.value`到達企業を抽出、参加者増員余地を可視化。NRR/拡大MRRをレポートに追加。
6. **更新提案モデルの追加**: `RenewalProposal { contractId, proposedMrr, expansionDelta, proposedAt, decidedAt, outcome }`を新設し、T-60マイルストーンと連動させる。
7. **オーナーUser化**: `ownerName: string` → `ownerUserId`参照。担当者ごとの稼働ヒートマップ画面を`attendance/`または`me/`に追加。

### P2 — オペレーション強化

8. **TTV指標の集計**: `AccountJourney.history`差分から平均到達日数を計算しレポートに表示。研修別・担当別で比較。
9. **通知/エスカレーション**: Health Red・Stuck・T-30未着手をSlack通知するフックを定義（`lib/notifications/`）。
10. **週次レビューのナレッジ化**: Goodタグ付与・全文検索・他社事例参照導線をWeeklyに追加。
11. **出席率の累積ビュー**と**欠席多発参加者の自動アラート**を`attendance/`に追加し、Healthへ連動。
12. **再アプローチKPI**: Churn → 再受注率/期間/勝因を集計するレポートセクション。

## 結論

「情報が整理されたCSポータル」としてはB+、「**CSが解約を防ぎ収益を伸ばすための作戦盤**」としてはC-。最大の問題はHealthスコアと更新マイルストーンが**信頼できないシグナル**になっていること、そしてCS as a Profit Centerを実装している痕跡が無いこと。P0の3点を是正しないままパイロット運用に入ると、「数字は出るが誰も信じない」状態になり、結果としてCS部門の意思決定が経験と勘に逆戻りする。

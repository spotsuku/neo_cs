## 2. P0 セキュリティ是正案 (基盤完了を待たず即着手可能)

### 2-1. CORS 全許可の是正

**現状**: 4ファイルすべてが `Access-Control-Allow-Origin: *`
- [api/auth.js:14](api/auth.js#L14)
- [api/db.js:11](api/db.js#L11)
- [api/db-all.js:9](api/db-all.js#L9)
- [api/claude.js:4](api/claude.js#L4)

**是正方針**:
1. 共通ミドルウェア `api/_cors.js` を新設し、各ハンドラの先頭で `applyCors(req, res)` を呼ぶ。
2. 許可オリジンは環境変数 `ALLOWED_ORIGINS` (カンマ区切り) で管理。
   - 本番: `https://cs.neoacademia.jp`
   - ステージング: `https://staging.cs.neoacademia.jp`
   - ローカル: `http://localhost:3000`
3. `Origin` ヘッダがホワイトリストに**一致した場合のみ**該当値をエコー、`Vary: Origin` を必ず付与。
4. preflight (`OPTIONS`) も同経路で処理し、許可外オリジンは **204 を返さず 403 + 空ヘッダ**。
5. `Access-Control-Allow-Credentials: true` はクッキー認証導入時のみ追加 (現状は不要)。

**擬似コード** (`api/_cors.js`):
```js
const allowed = (process.env.ALLOWED_ORIGINS || '').split(',').map(s => s.trim()).filter(Boolean);
function applyCors(req, res) {
  const origin = req.headers.origin;
  if (origin && allowed.includes(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Vary', 'Origin');
    res.setHeader('Access-Control-Allow-Methods', 'POST, OPTIONS');
    res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');
    res.setHeader('Access-Control-Max-Age', '600');
    return true;
  }
  return false;
}
module.exports = { applyCors };
```

### 2-2. `/api/claude` 無認証プロキシの是正

**現状の問題** ([api/claude.js](api/claude.js)):
- 認証なし → 第三者が `ANTHROPIC_API_KEY` を無制限に課金消費可能
- リクエストサイズ上限なし → OOM 攻撃ベクタ
- `model` / `max_tokens` を呼び出し側が自由指定 → コスト爆発
- エラーメッセージをそのままクライアントへ返却 → 内部情報漏洩

**是正方針**:
1. **認証必須化**: Authorization Bearer ヘッダで Supabase JWT を検証 (基盤01のセッションと統一)。未認証は 401。
2. **リクエストサイズ上限**: bodyParser で **32KB** 上限。`server.js` 側 `parseBody` にも同制限を入れる ([server.js:31-40](server.js#L31-L40))。
3. **モデル/トークンの固定**: サーバー側で `model` と `max_tokens` をハードコード or 環境変数化。クライアント指定は無視。
4. **レート制限**:
   - per-user: 60 req / 5min
   - per-org: 600 req / 5min
   - per-IP: 30 req / min (未認証フォールバック)
   - ストアは Supabase もしくは Upstash Redis (Vercel連携簡易)
5. **構造化ログ**: 呼び出しごとに `{user_id, org_id, model, input_tokens, output_tokens, latency_ms, status}` を `claude_api_calls` テーブルに記録 (コスト監査+ストリームC観測性の起点)。
6. **タイムアウト**: 30秒 (現状は無設定 → ハング可能性)。
7. **エラーマスキング**: 5xx は固定文 `{ error: 'internal_error', request_id }` のみ返す。詳細は構造化ログへ。
8. **Anthropic 同意フロー (A項)**: メール本文等の個人データを送る経路では、組織の同意フラグ (`organizations.anthropic_consent_at`) を必ず確認、未同意は 403。

### 2-3. `index.html` Stored XSS の是正

**現状の問題**: `innerHTML = ...` 経路がユーザー入力 (企業名・面談メモ・アクションテキスト・ユーザー名等) を**エスケープなしで埋込**。`localStorage` 経由で Supabase に同期され**全社員画面で発火する Stored XSS** ([reviews/11_情シスセキュリティ.md:77-82](reviews/11_情シスセキュリティ.md#L77-L82))。

**是正方針 (二択)**:

#### 方針A (推奨・整合性高): 旧 `index.html` の段階的廃止
- `commit d1c5720 CSポータルv3へ全面リニューアル` で Next.js v2 への移行は意思決定済。
- v2 への機能移植が完了した画面から `index.html` の該当ルートを削除、最終的に `server.js` の静的配信を撤去し、`/api/claude` のみを残す軽量プロキシに転換。
- スコープが大きいため**ストリーム02 (機能改修) と並走**。本ストリームは「廃止までの間、旧ポータルへ書き込み権限を奪う」防御策に責任を持つ。

#### 方針B (緊急止血): 旧 `index.html` 凍結
- 旧ポータルを **読み取り専用モード**へ強制切替: `LS.setArr` および `/api/db` の POST/DELETE を旧フロントから一律拒否 (Origin/Refererベース判定 + サーバー側ガード)。
- `innerHTML` 直書き箇所は新規挿入を停止しても**既存DBに残った悪性ペイロードが描画時に発火**するため、合わせて以下を実施:
  - `server.js` 配信時に **CSP ヘッダ** を付与: `default-src 'self'; script-src 'self' 'nonce-...'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`
  - インラインイベントハンドラ (`onclick=...`) を多用しているため、CSP は **Report-Only から開始**し違反収集 → 段階強化
  - `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload` を追加

**初動推奨**: **方針B を即時適用 → ストリーム02と連動して方針A を6週間以内に完遂**。

## 3. `audit_logs` テーブル設計案 (01スキーマと同時投入想定)

### 3-1. DDL ドラフト

```sql
create table audit_logs (
  id              bigserial primary key,
  occurred_at     timestamptz not null default now(),
  actor_user_id   uuid references users(id),       -- nullの場合はsystem
  actor_role      text,                             -- スナップショット (退職後にも保持)
  organization_id uuid references organizations(id),
  action          text not null,                    -- 'create' | 'update' | 'delete' | 'read_sensitive' | 'login' | 'logout' | 'export' | 'consent_grant' | 'consent_revoke'
  entity_type     text not null,                    -- 'company' | 'contract' | 'weekly_review' | 'user' | ...
  entity_id       text,                             -- 対象主キー (text化で複合キーも収容)
  before          jsonb,                            -- 変更前スナップショット (update/delete時)
  after           jsonb,                            -- 変更後スナップショット (create/update時)
  diff            jsonb,                            -- フィールド単位差分 (任意・大きい場合は省略)
  request_id      text,                             -- HTTPリクエスト相関ID
  ip              inet,
  user_agent      text,
  source          text not null default 'app',     -- 'app' | 'api' | 'job' | 'migration'
  reason          text                              -- 法務要件: 削除/エクスポート時の理由必須
);

create index audit_logs_occurred_at_idx on audit_logs(occurred_at desc);
create index audit_logs_entity_idx      on audit_logs(entity_type, entity_id);
create index audit_logs_actor_idx       on audit_logs(actor_user_id, occurred_at desc);
create index audit_logs_org_idx         on audit_logs(organization_id, occurred_at desc);

-- RLS: 監査ログは admin と監査担当ロールのみ閲覧可
alter table audit_logs enable row level security;
create policy "audit_read_admin" on audit_logs for select
  using (auth.jwt()->>'role' in ('admin', 'auditor'));
-- INSERT は service_role のみ (リポジトリ層経由)
create policy "audit_insert_service" on audit_logs for insert
  with check (auth.role() = 'service_role');
-- UPDATE/DELETE は禁止 (改ざん不可性)
-- 物理削除が必要な場合は別 retention ジョブで partitioning + drop
```

**保管期間**: 法務レビュー結果を待ち、**個人情報保護法・電子帳簿保存法の長い方+1年**を仮置き (7年)。`pg_partman` で月次パーティション化前提。

### 3-2. リポジトリ層へのフック注入インターフェース (01へ申し送り)

01が `lib/repository/` を作る際、以下の契約に従ってもらえると04側のフック実装が共通化できる:

```ts
// lib/repository/_base.ts (01側で実装してほしい契約)
export interface RepoContext {
  actor: { userId: string; role: string; organizationId: string };
  request: { id: string; ip: string; userAgent: string };
}

export interface MutationHook {
  beforeWrite?(payload: { entityType: string; entityId?: string; before?: unknown; after: unknown; ctx: RepoContext }): Promise<void> | void;
  afterWrite?(payload:  { entityType: string; entityId: string;  before?: unknown; after: unknown; action: 'create'|'update'|'delete'; ctx: RepoContext }): Promise<void> | void;
}

export function registerHook(h: MutationHook): void;
```

→ 04側は `lib/repository/hooks/audit.ts` を実装し、`afterWrite` で `audit_logs` に INSERT。`before/after` 差分は `fast-json-patch` 等で算出。
→ 01がこの契約を採用してくれれば、04側は**画面コードに一切手を入れず**監査記録を全変更に注入可能。

### 3-3. 「読み取りも記録すべき機微フィールド」の特定 (法務観点)

下記アクセスは `read_sensitive` として記録対象とする想定:
- メール本文・面談ログの個別表示
- 顧客個人 (受講生) の連絡先・属性
- エクスポート系 (CSV/PDF) 全般
- 設定変更 (ロール付与・剝奪、削除フロー実行)

→ リポジトリ層 `findById` 系に `markSensitive()` フラグを付ける運用で実装予定。

import { churnSignalRepo, contractRepo, companyRepo, userRepo } from '@/lib/repository';

const newSignals = await churnSignalRepo.listUnnotified({ severity: ['high', 'critical'] });
for (const sig of newSignals) {

  const company  = await companyRepo.getById(contract.companyId);
  const owner    = await userRepo.getById(sig.assignedUserId ?? '');
  await notifyChurnSignal({
    signalId: sig.id,
    contractId: sig.contractId,
    companyName: company.name,
    severity: sig.severity,

    evidence: sig.evidence,
    healthScore: sig.healthScore,
    detectedAt: sig.detectedAt,

    ownerSlackUserId: owner?.slackUserId ?? null,
    ownerName: owner?.name ?? null,

`/companies/[id]` 修正後の `npm run build` で `Module not found: Can't resolve 'pino'` が発生。原因は私の旧 `import('pino' as string)` が webpack の静的解析を回避できていなかったこと。

```ts
const dynImport = new Function('m', 'return import(m)');
export async function optionalImport<T>(specifier: string): Promise<T | null> {
  try { return await dynImport(specifier) as T; } catch { return null; }
}
```

`new Function` 経由でバンドラから不可視化、未導入パッケージで build を破壊しない真の動的 import を実現。以下7ファイルの `import('xxx' as string)` を全て `optionalImport()` 呼び出しに置換:

| ファイル | パッケージ |
|---|---|
| `lib/observability/logger.ts` | pino |
| `lib/observability/sentry.ts` | @sentry/nextjs |
| `lib/repository/audit.ts` | @supabase/supabase-js |
| `lib/security/auth.ts` | @supabase/supabase-js |
| `lib/security/session.ts` | @supabase/supabase-js |
| `app/api/claude/route.ts` (logCall) | @supabase/supabase-js |
| `app/settings/consents/actions.ts` | @supabase/supabase-js |

各ファイルは未導入パッケージの型情報を**最小限のローカル interface** で表現 (`SupabaseClient`/`SupabaseModule`/`MinimalSentry`) し、`typeof import(...)` の tsc 解決依存を排除。

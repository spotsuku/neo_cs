## フェーズ1: 現状把握 (完了)

### 1-1. supabase_schema.sql の現状
- 単一テーブル `ps_data(id bigserial, key text unique, value jsonb)` のKVS構造のみ ([supabase_schema.sql:5-10](../supabase_schema.sql#L5-L10))
- RLSは `enable` だけして `for all using (true) with check (true)` の全開放ポリシー ([supabase_schema.sql:25-30](../supabase_schema.sql#L25-L30))
- インデックスは `key` 単独のみ。JSONB GIN なし。`created_at` すら無い (`updated_at` のみ)

- **全顧客データが同一JSONに同居**しているため、本番運用は事実上不可能

- `HealthScore.factors` は型のみで `factors:{}` 固定 — 因果が逆 (color → score)
- イベントログ・スナップショットの永続化先が無い → 時系列分析・ML不能

### 1-3. api/auth.js, api/db.js の現状
- [api/auth.js](../api/auth.js) — Google ID Tokenを `verify` 時のみ検証。CORS全開、`aud`/`hd` 検証なし
- 認可は **body内のemail自己申告** (`api/auth.js:58-77`) — 任意ユーザー昇格脆弱性
- 初回ユーザー自動admin化 (`api/auth.js:106-107`) — レース条件で外部Googleアカウントが管理者を奪取可能
- セッション・JWT・Cookie発行なし。ロールはレスポンスJSONで返してクライアント任せ
- [api/db.js](../api/db.js) — **完全無認証**で `ps_data` の read/write/delete を anon key で代行。誰でも `curl` で全件抜ける
- PostgRESTフィルタに `encodeURIComponent(email)` のみ — **フィルタインジェクション**の余地あり (16_SRE指摘)

### 1-4. v1 / v2 の関係
- **v1**: `index.html` (7,238行のSPA) + `server.js` (生Node静的配信) + `api/*.js` (Vercel Functions風ハンドラ) — ルート直下
- **v2**: `neo-cs-v2/` (Next.js 16 App Router) — モックデータ駆動、永続化なし。最近のコミットで「CSポータルv3へ全面リニューアル」 (`d1c5720`)
- v1の `index.html:676,882,1268,1464,...` で `innerHTML` に未エスケープ埋め込み → **Stored XSS**
- v1とv2は **共存しているだけで連携していない**。同じ `ps_data` を読み書きする可能性はあるが、データ形状の互換は保証されていない (14_将来運用者指摘)
- **方針**: v1 (`index.html`/`server.js`/`api/*.js`) は完全廃止し、v2 のRoute Handler (`app/api/*`) に統合する。これは情シス/SRE/法務レビューでも一致した結論。

## フェーズ2: 正規化スキーマDDL案

### 設計方針
1. **ドメインモデル本位**: `lib/mock/entities.ts` 等の型を正本に、サイクル非依存層（Account/People/Master）とサイクル依存層（Contract/Cycle）を明確分離
2. **時系列の器を最初から用意**: `health_score_snapshots` (日次), `account_journey_events`, `contract_status_events`, `attendance_events` を分離
3. **監査列を全テーブルに**: `created_at / updated_at / created_by / updated_by` (auth.usersへのFK) + 重要テーブルは `audit_logs` で別途追跡
4. **RLSは認証uidベース** — `allow_all` を全廃。後述の方針セクション参照
5. **法人番号 (corporate_number 13桁)** をcompanies.uniqueに導入（07_アナリスト指摘）
6. **金額は `numeric(12,0) jpy` に統一**（税抜想定、税区分は別カラム）
7. **手書きID (`c-aeon` 等) はmigration時のみ保持**するため `legacy_id text unique` を持たせ、PKは `uuid default gen_random_uuid()`

### RLSポリシー方針 (B/C項)

#### 共通原則
- すべてのテーブルで `enable row level security` + **`allow_all` 撤廃**
- `anon` ロールにはデフォルト全拒否
- 認証は `auth.uid()` が `app_users.id` と一致することを起点

#### 想定パターン
- **admin**: 全テーブル全行 R/W
- **manager**: 全企業の閲覧可、編集は所属チームの担当案件のみ
- **member (CS担当)**: 自分が `companies.owner_user_id` の企業 + 同じ企業を担当する `contracts.owner_user_id` の契約に紐づくデータのみ R/W
- **viewer**: read-only、機微情報 (`contacts.email`, `contacts.tel`, `meeting_logs.summary`等) はマスク

#### サンプル (companies)
```sql
alter table companies enable row level security;

-- 自分が担当する企業のみread。ただしadmin/managerは全件read
create policy companies_read on companies for select using (
  exists (select 1 from app_users u
          where u.id = auth.uid()
            and u.is_active
            and (u.role in ('admin','manager') or companies.owner_user_id = u.id))
);

-- write: admin/manager または担当者本人
create policy companies_write on companies for all using (
  exists (select 1 from app_users u
          where u.id = auth.uid()
            and u.is_active
            and (u.role in ('admin','manager') or companies.owner_user_id = u.id))
) with check (
  exists (select 1 from app_users u
          where u.id = auth.uid() and u.is_active
            and u.role in ('admin','manager','member'))
);
```

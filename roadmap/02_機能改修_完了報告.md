## 注意点・次セッションへの引き継ぎ

### 1. 保存後の画面再描画について
mock リポジトリは新規 `WeeklyReview` を `weeklyReviews` 配列とは別の `store` に持つ。**保存しても画面側はそのまま `weeklyReviews` (mock seed) を参照しているため、保存後にリロードしても変更が反映されない**。これは仕様 (mockのライフサイクル) の制約。

ストリーム01が Supabase 実装に進んだ時点で:
- `WeeklyReviewPanel` / `CompanyWeeklyEditor` の冒頭で `weeklyReviewRepo.list()` を `useEffect` ベースで呼ぶようにリファクタ
- もしくは Server Component 化して props で受け取る

までセットで対応しないと、保存→再表示の体験は完成しない。

### 2. 日付・週ラベル算出
`WeeklyReviewUpsert` 型は `weekEnd` `weekLabel` を含まず、`mockWeeklyReviewRepo.upsert` 内で `getWeekRange(weekStart)` から自動算出する設計になっている。これは意図的な設計 (DBには weekStart のみ持って、表示用は計算で導く)。upsert 呼出側は `weekStart` のみ渡せばよい。

### 3. companies/new の Company 型不整合
mock の `Company` 型には `employeeSize`/`websiteUrl`/`foundedYear`/`primaryContact*`/`slackChannel` が無い。本セッションでは memo 欄に集約して保存。Supabase 実装時には:
- `company_contacts` テーブル(主担当連絡先)
- `companies.website_url`, `companies.founded_year`, `companies.employee_size_range` 等
を追加するのが正しい。`01_基盤_DDL案.sql` の `company_contacts` が既にあるので、Supabase ドライバ実装時にスキーマ拡張で吸収。

### 4. デザイントークン
ストリーム03は提案フェーズのみで、`tailwind.config.ts` への semantic token (success/warning/danger 等) は未追加。本セッションは既存トークン (`emerald-*`/`rose-*`/`ink-*`/`liquid-surface`) のままで作業。03の実装が走った後、機械置換でトークン化する想定。

### 5. 「下書き保存」と「完了としてロック」の意味分離
- 下書き保存: `locked: false` で upsert (保存はするが未確定として再編集可)
- 完了としてロック: `locked: true` で upsert (確認ダイアログ後)。週固定後は再編集不可
両者ともリポジトリへの書き込みは発生する。仕様レビュー04(CS入力者)推奨の「明示保存」モデルに整合。

### 6. CURRENT_AUTHOR ハードコード
両週次画面で `const CURRENT_AUTHOR = "古野"` を埋め込んでいる。**B項(メンバーマスタ)で `userRepo.getCurrent()` から取得**するように差し替えること。今は技術的負債として明示マークしている。

## C項: Healthスコア再設計 — 完了

### C-1. factor → score の純関数化 (因果反転の是正)

新規モジュール: [`lib/domain/health.ts`](../neo-cs-v2/lib/domain/health.ts)

5因子の重み付き加算 (合計100):

| 因子 (HealthFactorKey) | 重み | 正規化 (悪い→0、良い→100) |
|---|---:|---|
| `attendance` (出席率) | 25 | 0..1 → 0..100 |
| `weeksSinceLastTouch` (接点鮮度) | 20 | 0週=100, 4週=50, 12週+=0 |
| `overdueOnboardingTasks` (期日超過件数) | 20 | 0件=100, 5件+=0 |
| `negativeSignalCount` (ネガティブ件数) | 20 | 0件=100, 4件+=0 |
| `milestoneProgress` (T-120/90/60/30 done比率) | 15 | 0..1 → 0..100 |

閾値: green ≥ 75, yellow ≥ 55, red < 55

純関数 `computeHealthScore(factors, computedAt?)` → `HealthBreakdown` を返す。`HealthBreakdown.contributions` に各因子の `weightedScore` / `tone` / `hint` を含み、UIで寄与度を可視化できる。`topNegative` は失われた寄与が最大の因子 (=最大の改善ポイント)。

mock移行用補助:
- `deriveMockFactors({contractId, baselineColor})` — 既存 Contract.healthScore.color から決定論的に factor を逆生成 (mock時代の暫定。Supabase切替時は実データに置換)
- `computeFromContract(contract)` — Contract → HealthBreakdown のショートカット

Supabase 切替時はサーバー側日次バッチ (`health_score_snapshots` への INSERT) が同じ `computeHealthScore` を呼ぶ。

### E-1. lib/domain/kpi.ts (純関数)

新規モジュール: [`lib/domain/kpi.ts`](../neo-cs-v2/lib/domain/kpi.ts)

**設計原則** (health.ts / churn.ts と同じ):
- Repository 非依存。契約配列・解約配列・サーベイ等のファクトを引数で受ける
- 全 KPI が `breakdown` (formula + 内訳 + contributingIds) を返す → UIで「計算根拠」モーダルが描ける
- 期間境界は from <= occurredAt < to の半開区間で統一
- monetary は `numeric(12,0) JPY` 整数 (税抜)

**公開API**:

| 関数 | 戻り値 |
|---|---|
| `periodFor(key, asOf)` | `PeriodWindow` (key, label, from, to) |
| `computeMrr(contracts, asOf)` | `MrrBreakdown` (totalMrr, byProduct, bySegment, contributingContractIds, formula) |
| `computeArr(contracts, asOf)` | `ArrBreakdown` (= MrrBreakdown + totalArr) |
| `computeChurnRate(contracts, period)` | `ChurnRateBreakdown` (rate, churnedMrr, startMrr, churnedContractIds) |
| `computeNrr(contracts, period)` | `NrrBreakdown` (rate, startMrr, expansion, downgrade, churn, endMrr) |
| `computeAtRiskMrr(contracts, signals, asOf)` | `AtRiskMrrBreakdown` (high severity 未解決シグナルを持つ契約の MRR 合計) |
| `computePeriodPerformance(contracts, period)` | `PeriodPerformanceBreakdown` (newContracts/newLogos/renewed/churned + MRR純増減) |
| `computeMrrTrend(contracts, monthsBack, asOf)` | 月次 `{month, mrr}[]` |

**会計年度の判定**:
- 4月始まり (FY26 = 2026/4/1〜2027/3/31)
- `fiscalQuarterIndex(asOf)` で Q1..Q4 を算出
- Q1 と FY は from/to が **別物** になり、`computePeriodPerformance` が独立した結果を返す → **Q1=FY不具合の根本解消**

| skipped | ❌ | ❌ | ✅ (idempotent) |
